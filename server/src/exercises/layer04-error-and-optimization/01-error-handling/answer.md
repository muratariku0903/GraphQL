# 演習4-1: エラーハンドリング — 言語化回答

## Q1: GraphQLのエラーモデル — なぜHTTP 200なのか

### なぜHTTP 200固定なのか

理由としては2点ほどあります。まず1点目としては、設計思想の観点で HTTP の通信が成功したかどうかというレベルで 200 か否かを GraphQL の中では考えています。つまり、アプリケーションの処理が失敗したかどうかというのは HTTP のステータスには関与しないという考え方ですね。通信が成功したら 200、サーバーがダウンしたら 500 っていう、そういうレベルで考えているので、GraphQL の中でのエラーっていうのは HTTP 側には特に通知することなく、常に 200 で返すということです。

逆に言うと、HTTP のステータスによってアプリケーション側が何かしらの制御することがありません。基本的に GraphQL 内のエラーオブジェクトを基づいてクライアントがそれを見てよしなに処理をするっていう、アプリケーションの中で起きたことはアプリケーションの中でやるみたいな、そういう設計思想です。2点目としては、そもそも GraphQL の設計上、複数の項目を一つのクエリで扱えるっていうところがあります。REST とかだとエンドポイントに対して一つのレスポンスっていうのが確定していると思うんですけども、GraphQL の場合は一つのエンドポイントに対して無数のレスポンスが存在していて、各フィールドごとに値を解決するという考え方になります。

### 部分エラー（partial response）とは

部分エラーとは、クエリが複数の項目を返すケースで一部の項目の取得に失敗している場合に発生するケースになります。例えば、AとBという項目を返すとなったときに、Bのリソース解決が失敗してしまった場合、Aは存在するけどBはヌルみたいな感じになります。

最終的なエラーレスポンスとしては、「エラーズの中にBがこうこうこういう理由で失敗しちゃいました」とような、部分的には取得成功してるけど部分的には失敗してるみたいなところをまとめてレスポンスに含めているっていうのが部分エラーの特徴になります。この場合でもステータスは200になります。

### HTTP 200固定のデメリット

様々な点でメリットが存在しますが、一つ目としては HTTP インフラの統合がやりにくいという点です。HTTP インフラというのは、基本的にはステータスコードを見て、そのコードに応じてキャッシュしたり、HTTP の中での何かしらの処理が走る仕組みがありますが、そういった恩恵がずっと 200 のままだと得られないケースがあります。例えば、認証失敗した場合でも 200 を返すと、HTTP インフラ的には 200 が来たと判断して、そのデータの内容をキャッシュしてしまうことがあります。失敗したデータの内容をキャッシュしちゃって意味がないですよね。そのため、うまく使いこなすことができない点です。

二点目としては、監視・監査がしにくいという点です。監視ツールとしては DataDock や Sentry などがあると思いますが、これらは基本 HTTP のステータスが 500 とか 400 などの場合にアラート通知したり、トリガー設定ができるようになっています。しかし、GraphQL の場合、常に 200 を返すようになってしまうため、そこのアラートの設定が難しいという点があります。そのため、別途設定が必要になります。

三点目としては、セキュリティの部分で、WAF であったりゲートウェイがステータスコード 200 を判断して、何か失敗しているのに 200 が返ってきてくることで、何か侵入されちゃったんじゃないかというような誤解を招きかねないという点があります。

## Q2: errors配列 vs Union型Result パターン

### それぞれのメリット・デメリット

Errors配列のメリットとしては、まず実装がシンプルですね。Resolverでスローを出せば、そのままGraphQLのデフォルトのエラーインターフェースを用いることができるので、比較的工数が少なくエラーハンドリングができます。また、オプショナルエラーなども対応できるため、部分的な成功と失敗が共存した状態でエラーを返すことができるのもメリットです。

デメリットとしては、クライアント側でそれを処理する際に型安全性が低いことが挙げられます。どんなエラーなのかをクライアント側で文字列の比較などを通して検証する必要があるため、ヒューマンエラーによる意図しない挙動が発生するリスクがあります。

一方、ユニオン型リザルトの場合は、ちょっと実装が複雑化してしまうものの、クライアント側でスキーマを元にエラーの型を自動生成させることができるので、不正な構文であればコンパイルエラーで防ぐことができます。先ほども述べたように、デメリットとしては実装が少し複雑になってしまうことが挙げられます。

### Union型パターンが特に有効なケース

ビジネス的な想定得るエラーに対するクライアントのミューテーションの挙動の変化に対応するケースですね。あらかじめ業務要件で、「こういうエラーが起きたときはこういう挙動を取ってほしい」というような要望があった場合は、それだけ別のユニオン型として定義してあげて、クライアントでそれを解釈するというようなケースで有効かなと思います。

### 両者の併用と使い分け

基本的なエラー、インターナルサーバーエラーだったり認証エラーだったり予期せぬエラーっていうのは、基本的にはエラー図っていうデフォルトのインターフェースを用いて、ビジネス預金に関わる想定内のエラーに関してはリザルト型を使ってそれ専用の型っていうのを定義してあげると使い分けしやすいかなと思います。

## Q3: formatError と例外フィルター

### formatError の役割

クライアントへのエラーの形式を統一するのが主な役割になります。

### NestJSの HttpException をGraphQLで使うと何が起こるか

 HTTP Exceptionsのステータスコードによらず、すべて500としてインターナルサーバーエラーとして解釈されてしまいます。またスタックトレースなどが全て吸収されてしまうので、思わぬ情報漏洩などにもつながる可能性があります。

### formatError と例外フィルターの責務の違い

 FormatErrorっていうのは、クライアントに対してエラーの形式を揃えるっていうところが責務になってます。例外フィルターっていうのは、NestJSがスローする例外を適切にGraphQLのエラーの形に変換するっていうのが責務になります。なので、両者は変換という意味では同じなんですけど、FormatErrorは形式を整えるということに対して責任を持っているっていうのと、例外フィルターっていうのはGraphQL以外のレイヤーで発生したエラーをGraphQLのエラーとしてフォーマットするためのものになります。
