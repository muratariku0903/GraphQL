# 演習4-2: パフォーマンス最適化 — 言語化回答

## Q1: GraphQL特有のパフォーマンスリスク

### リスクの列挙と具体例

1. ネストがめちゃくちゃ深くなっちゃうっていうリスクがあります。クライアントが例えば Book っていうクエリを呼び出したときに、その Book の中のオーサーの中のといった感じでどんどんどんどん項目をネスト指定することで、負荷の高い呼び出しっていうのを実行することができてしまいます。

2. 2点目は 1点目の深さとはまたちょっと違くて、横の広さ、要は大量な項目を取得するように宣言するケースです。例えばオブジェクトがあったときに、それらの中で Book っていうオブジェクトがあったときに、その Book っていうのが大量の項目からなるものだったときに、その Book の配列を全部の項目取得するみたいなケースですね。横に広く取ってくるっていうリスクとかそういうケースが考えられます。

3. 3つ目は Alias を使った連打っていうので、同一のクエリっていうのを Alias を使って複数並べて、1リクエストで N 回分の負荷っていうのを発生させることができます。

### RESTではなぜ起きにくいか

RESTでは、クライアントがレスポンスの形を指定することができず、APIを提供している側で定めてしまうため、どういう結果が返ってくるかは決まっています。そのため、GraphQLのような問題は起きにくいかなと思います。

クライアントがレスポンスを指定できるという点は、本質的なリスクになります。

### 柔軟性とサーバー保護のトレードオフ

GraphQL の場合は、クライアントがリクエストを指定してレスポンスの形を指定できるという柔軟性があります。ただし、その分、クライアントが危険なクエリ呼び出しを実行し、サーバーに対して危害を加える可能性が出てきます。

そのため、柔軟性とウォーターを取る代わりにサーバーの負荷が大きくなってしまうため、そこの保護は別途考えなければならないと思います。

## Q2: Query Depth Limiting

### 深いネストが危険な理由

NESTされるたびにクエリの実行回数っていうのが指数関数的に増加して、わずかなNESTで膨大な数のクエリを実行することが可能になります。例えば、Bookっていうクエリをたたいたとして、そこからオーサーをNESTして取ってくれば、いいサーレンスのオーサーからオーサーIDに紐づくブックスっていうのを全部取ってきて、またさらにそこにブックスに一つ一つに紐づくオーサーを取ってくるってなったときに、どんどんどんどんネストが5個ぐらい積み重なった結果だけでも、もう数十万ぐらいのクエリが実行されてしまうっていうのが考えられます。

そのため、少ないNESTでも大規模なクエリ実行できるっていうところが危険な点かなと思います。

### 適切なDepth Limitの決め方

そのクエリで対象としているオブジェクトの必要最低限の深さプラスちょっと余裕のある深さぐらいがリミットとして適切な値かなと思います。例えばカントリーというオブジェクトがあり、そこに都道府県であったり市区町村であったり、バンチゴーとどんどんどんどん、そもそもそのオブジェクトが多くの構造を含んでいる場合、そういった場合は場合によってはネストは深く設定しなければならないと思います。

じゃないと、深部のデータまだ取ることができないため、そこは実際のどれぐらいのデータが取れるのか、どれぐらいの負荷がかかるのかっていうのは計測したほうがもちろんいいと思うんですけど、そもそものそのオブジェクトの構造の深さっていうのを前もって特定して、それを満たせる深さプラスちょっと余裕を持たせるぐらいが良いと思います。なのでそのオブジェクトごとにリミットデプスっていうのは異なってくるかと思います。

### Depth超過時のエラー設計

Resolver でバリデーションみたいなのをセットする、あるいはパイプみたいな感じでバリデーションのレイヤーで深さチェックをして、深さを超えてた場合は即座にバリデーションエラーとして返すっていうのがシンプルかなと思います。

## Q3: Query Complexity Analysis

### フィールドごとのコスト基準

単一のフィールドであったら、そこまでコストっていうのは大きく見積もる必要はないかと思います。ただ、リレーションフィールドであったりリストフィールドっていうのは複数のクエリの解決が必要になるので、コストも大きくなりがちになるかと思いますので、そこはコンプレクシティなどを吉田に設定していく必要はあるかなと思います。

なので、フィールドごとにコストを割り当てる基準っていうのは、それが単一なのか、複数のフィールドによって成り立っているのかっていう、複数のフィールドというか複数のクエリ実行が必要なのかっていうところになると思います。

### multiplier（乗数）の概念

条件の概念とは、件数やリストで取得するときに必要になってきます。例えば、このフィールドはスコア1ですと定めた場合、そのフィールドに対してその中の件数を考慮できていない状態となります。例えば、ページネーションで先頭から1件取得したとしても、100件取得したとしてもスコアは1となってしまい、これは実際の負荷を考慮できていません。

常数の概念を取り入れることで、取得してくる件数を正しくスコアに反映することができます。例えば、100件だったら100かけるスコア分1をかけ、全体のスコアとしては100となります。このような感じで、内部で取ってくる件数に応じて、正しく反映させる仕組みとして「上数」の概念があります。

例えば、Q1のデプスのところでも、Q2かQ2でクエリデプスリミッティングという仕組みがありました。ネストされているクエリが件数を保持している場合、例えば10×10で100みたいな感じで、どんどん倍々にスコアが大きくなっていきます。そういった場合に、特に正しくスコアを反映することができるようになります。

### Query ComplexityとDepth Limitの役割の違い

クエリコンプレクシティは、そのフィールドごとの複雑度を測るために使われます。例えば、Booksというフィールドがあった場合、そのBooksのクエリを実行するためにどれぐらいの複雑度になるかを測る水準として使われます。

一方、デプスリミットは、クエリがどれぐらいネストされているかを設定するためのものです。一つだけでは不十分で、フィールドごとの負荷を見ることも必要ですし、クエリのネスト数も見なければなりません。クエリコンプレクシティだけでは、Booksという単一のフィールドのスコアを見てしまい、デプスの中で無限にネストされる事態を防げません。また、デプスリミットだけでは確かにネスト数を制限できますが、フィールドごとの負荷を考慮できないため、フィールドの複雑度を狙った攻撃を防ぐことができません。

## Q4: Persisted Queries

### 解決する問題

登録された事前に登録されたクエリ以外を実行しないっていうルールを設けることによって、根本的な脆弱性の解決が可能です。例えば、Q2とQ3っていうのは、クエリの複雑度であったり、何回ネストされてるかっていうのを見て弾いたりするんですけど、そもそもこのPersisted Queriesっていうのは登録されたハッシュ値を送るんで、クライアントがそういったハッシュ値を送るんで、そもそも危険性のあるクエリをクライアントが実行できなくなるっていうものです。

Persisted Queriesの設定を手動でやっている場合、Q2とQ3の対策はほぼ必要ないのかなと思います。何でかというと、クライアントがそういった危険なクエリを実行することができなくなるからです。クエリそのものをクライアントが指定するのではなくて、クライアントからはハッシュ値を指定するようになるからです。

ただ注意しなければいけないのが、Persisted Queries の登録を APQ を使って自動化してしまう場合は、Q2 と Q3 の対策は別途必要です。なぜかというと、Q2 と Q3 のクエリのルールを突破したものだけが事前に登録され、2 回目以降のクエリのやり取りはそのハッシュ値を使って行われるからです。
なので初回突破されちゃうと意味がないので、Q2 と Q3 の対策は必要です。

また、パフォーマンス面でもクエリがそのまま文字列として送られてくることがなくなり、短いハッシュだけを送ればよいことになるので、リクエストのトラフィックの量も削減することでパフォーマンスの向上が期待できるかと思います。

### APQの仕組み

Persisted Queries を設定するには、手動と APQ という 2 つの方法があります。APQ の場合は設定を自動化することができます。手動であらかじめ「このクエリは許可します」といった設定を CI/CD に組み込むよりも、導入コストを低く抑えることができます。

仕組みとしては、最初の初回リクエストでクライアントがクエリをリクエストします。そのクエリがバックエンドで実行され、完了されると、初回リクエストの場合はまずありません。バックエンドに登録されていないので、その場合はハッシュ値を送っても、ハッシュ値単体だけ送っても意味がありません。クライアントに「クエリ本文を実行してください」というように命令します。

そのため、初回リクエストの場合はクライアントはハッシュ値と、そこに対応するクエリ本文の 2 つをサーバー側に送信します。サーバー側がそのクエリが実行できると、ハッシュ値を登録するようになります。2 回目以降は、キャッシュされているハッシュ値でやり取りするという形になります。

大事なのは、初回リクエストのクエリ本文がサーバー側でちゃんとルールに基づいて「これは許可する」「これはダメ」といった設定をしておくことです。これが緩いと、どんなクエリだとしてもハッシュとして保存されてしまって、2 回目以降も普通にそのハッシュでやり取りできてしまうので、MyAPQ を考える場合は、問 Q2、Q3 で設定した脆弱性の対応が必要です。

### Persisted Queries Onlyモードと運用

本番環境ではPersisted Queries Onlyモードを使うのが一般的です。開発環境ではそのモードを外すことが多いです。本番環境では、外部のユーザーがアクセスできる可能性があるため、セキュアな設定を重視したほうが良いです。

一方、開発環境では本来隔離されていることがほとんどであり、外部からのアクセスは二の次になります。どちらかというと、アドホックなクエリを実行したい場合もあるため、実験のためにPersisted Queries Onlyモードを外し、柔軟に検証できる状態を維持する考え方があります。
