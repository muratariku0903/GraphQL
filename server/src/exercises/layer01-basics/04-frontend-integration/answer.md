# 演習1-4: フロント統合 — 言語化回答

## Q1: urql の Exchange とは何か

### Exchange とは何か（Expressのmiddlewareとの対比）

Expressのミドルウェアと同じようなものなので、実際にリクエストを送信するまでの中間に処理を挟み込めるような仕組み。挟み込んだ順にミドルウェアが順番に実行されていきます。

### cacheExchange / fetchExchange / ssrExchange の役割

| Exchange | 役割 |
|---------|------|
| cacheExchange |ドキュメント単位でのキャッシュを設定できます。クエリをハッシュ化して、それをキーに設定し、値にクエリの結果を保存します。重複したクエリを実行する場合は、キャッシュから値を返します。重複したクエリでなかった場合は、オリジンに取得しに行きます。オプションでキャッシュを強制したり、逆にキャッシュ無効化したりといった柔軟な制御が可能です。 |
| fetchExchange |リクエストの送信をしている処理のミドルウェアになります。内部でフェッチ関数を実行し、実際にクエリのエンドポイントに対して実行しています。 |
| ssrExchange |サーバーサイドでレンダリングされた結果をキャッシュとしてクライアントで使い回すための設定。Next.jsでは裏で勝手にやってくれますが、特にApp Router、それ以外だとサーバー側で取ってきたデータをクライアント側で使い回したいんだが、ハイドレーションされるタイミングで再度クライアント側がデータをオリジンに取得しに行ってしまう問題が発生するので、それは二度手間なので、サーバーで取ってきたデータっていうのをssrExchangeに蓄積して、それをクライアントからキャッシュとして利用するための仕組みです。 |

### 配列の順序が重要な理由

設定された順序でミドルウェアが実行されますので、その順序を間違えてしまうと意図した挙動になりません。例えば、Fetch Exchangeというのは最終的にエンドポイントにリクエストを飛ばす処理になるんですけども、もしこれを最初に行ってしまうとその後にCache ExchangeだったりSSR Exchangeをやったとしても実質意味がないことになります。なので、データの流れというのを意識する必要があって、最初にキャッシュをしてその後フェッチするという流れを考える必要があります。

### 📝 レビュー（Q1）

3観点すべて正確です。特に `ssrExchange` の「ハイドレーション時の二度取得を防ぐ」という説明は本質を捉えています。

**補足:**

**Exchange の実行順序について:**
Expressのmiddlewareとの重要な違いが1つあります。Expressは「リクエストが来た順」に1方向で流れますが、urql の Exchange は **双方向パイプライン** です — 上から下に「operation（リクエスト）」が流れ、下から上に「result（レスポンス）」が流れてきます。

だから `[cacheExchange, ssrExchange, fetchExchange]` の順序は：
1. operation が上から下に流れる: cache → ssr → fetch
2. cacheExchange でヒットすれば、その場で result を返して終了（下には流れない）
3. fetchExchange で取得した result が上に戻ってくる: fetch → ssr → cache
4. cacheExchange は返ってきた result をキャッシュに格納

**なぜ cacheExchange が最初（上）なのか:**
「キャッシュがあるなら fetch すら発火しないようにしたい」からです。もし順序が `[fetchExchange, cacheExchange]` だったら、毎回ネットワークリクエストが発生してしまい、キャッシュの意味がなくなります。

**なぜ fetchExchange が最後（下）なのか:**
fetchExchange は「実際のネットワーク通信を行う終端」だからです。終端 Exchange と呼ばれ、必ず下流に位置します。もし後ろに他の Exchange を置いても、fetchExchange が result を返すだけなので意味がありません。

→ この「双方向パイプライン」のイメージを持っておくと、Layer 4 以降でカスタム Exchange（認証トークン付与、リトライ、ロギング等）を書くときに理解が早いです。

Q1完了です。Q2に進みましょう。

## Q2: RSC vs Client Component でのGraphQL呼び出し

### 比較表

| 観点 | Server Component | Client Component |
|-----|-----------------|------------------|
| データフェッチのタイミング |サーバー側でデータを取ってくるので、ブラウザーがコンテンツを表示する前にリクエストの段階ですでにデータフェッチが実行されます。 |リクエストが実行され、コンテンツがブラウザにロードされ、JSとかもハイドレーションされて、サイトがアクティブになったときに実行されます。 |
| 初回ロードのUX |データフェッチのタイミングが早いので、単純にもう既にデータを取得している状態でユーザーはサイトを閲覧することになります。プラス、サーバコンポーネントの場合はバンドルサイズを削減できるので、ユーザーがサイトにアクセスしてそこからサイトがアクティブになる時間っていうのを削減できるので、初回ロードのUXはより良いものになるのかなと思います。 |サーバーコンポーネントに対して、クライアントコンポーネントの場合はユーザーがサイトにアクセスしてからサイトがアクティブになるまで待つ必要があります。で、そこからデータを取得しに行くので、最終的にデータがこうサイトに表示されるまでに、多少時間がかかる可能性が出てきます。そういう面で言うと、初回ロードの点で言うとサーバーコンポーネントよりはUXの価値っていうのは低下するかなと思います。 |
| インタラクティブ性 |インタラクティブな操作に関してはサーバーコンポーネントは向いてないかなと思います。基本的に何かしらのコンテンツを初期表示するときに使うものであって、ユーザーの操作と連動するためには様々なフックが必要で、そのフックというのはブラウザの環境で動くものなので、基本的にはユーザーの操作と連動するものに関しては適正はないかなと思います。 |インタラクティブな操作に関した useQuery は適しているかなと思います。ユーザーのボタンをクリックした時にデータ取得していたり、データをキャッシュしたり、データ取得中にローディングしたり、エラーが出たらエラーメッセージ表示したりっていう、いわゆるステート管理と useQuery というのを統合して管理できるものになると思うので、そういった制御をすごく簡潔にするためのフックでもあると思います。また、キャッシュ機能なども使えるので、ユーザーが何回も同じような処理をした時などはキャッシュのデータを返すといった効率化も図れるかなと思います。 |
| SEO |クローラーが初回にアクセスした際は、サーバーコンポーネントの場合はちゃんとコンテンツが表示されている状態なので、SEOの評価というのは良いものかなと思います。 |対してクライアントコンポーネントの場合は、おそらく最初にクローラーがアクセスして閲覧するものはシェルのみ、HTMLの外側だけになるので、クローラーからの評価っていうのは良くなくないものになるかなと。コンテンツが空の状態として見なされてしまうと思います。実際にデータが取ってこられるのは、その後ハイドレーションされてサイトがアクティブになった後になるので、それはそのクローラーからしたら初回のアクセスには見られないものになります。 |

### 書籍一覧ページではどちらを選ぶか

こちらはサーバーコンポーネントを使ってその中でGraphQL通信をするのが好ましいです。一覧ページなので、初回にデータを取ってきて表示すればいいだけですので、ユーザーの操作とかが入らないのであれば復活なども必要ないので、サーバー側でレンダリングしてそれを返せばいいかなと思います。そっちの方がUXだったりSEOの面でも有利かなと思います。

### 検索フィルタ付き書籍一覧ページではどちらを選ぶか

検索操作が入ると、Reactなどコンポーネントの状態管理が必要になるので、それと連動するような仕組みを考える必要があって、そうなるとサーバーコンポーネントというものを使えないので、useQueryなどを使ったクライアントコンポーネントベースでの処理が必要かと思います。

### 📝 レビュー（Q2）

4観点すべて的確で、書籍一覧と検索フィルタ付き一覧の使い分けも正しい判断です。特に「クライアントコンポーネントはシェルのみ初回表示される」というSEOの説明は正確です。

**補足 — 実務で多用される「ハイブリッドパターン」:**

実は書籍一覧も検索フィルタ付きも、**両方を組み合わせる**パターンが実務では主流です：

1. **初回表示はRSCで**: ページを開いた瞬間に表示される書籍一覧（検索条件なしのデフォルト状態）はServer Componentで取得
2. **検索操作以降はClient Componentで**: ユーザーが検索ボタンを押したら、その部分だけClient Componentで `useQuery` を実行

コードイメージ：
```tsx
// app/books/page.tsx (Server Component)
export default async function Page() {
  const initialBooks = await getClient().query(BooksQuery, {});
  return <BooksSearchClient initialBooks={initialBooks} />;
}

// app/books/books-search-client.tsx (Client Component)
'use client';
export function BooksSearchClient({ initialBooks }) {
  const [filter, setFilter] = useState('');
  const [result] = useQuery({
    query: BooksQuery,
    variables: { filter },
    pause: !filter,  // 検索条件がない間はQueryを実行しない
  });
  const books = result.data?.books ?? initialBooks;
  return <>{/* 検索UI + 一覧 */}</>;
}
```

このパターンの利点：
- 初回ロードは RSC の恩恵（高速表示、SEO対応）
- ユーザー操作はクライアント側で完結（インタラクティブ）
- `initialBooks` を Client に渡すことで、ハイドレーション時も検索前の一覧が既に見えている

→ このパターンは Layer 2 以降の演習や、internal-system の実装でも使うことになるので頭に入れておいてください。

Q2完了です。Q3に進みましょう。

## Q3: Mutation後のキャッシュ更新戦略

### 3つの戦略の比較

| 戦略 | メリット | デメリット |
|-----|---------|-----------|
| 自動更新（Mutationレスポンスに含める） |手軽にキャッシュ管理を実現できる点。 |細かいキャッシュ管理などが難しい。例えばクエリとその結果っていうのが丸ごとキャッシュで保存されているので、細かく差分を検証できない。大雑把にキャッシュがリフレッシュされちゃうし、場合によってはリフレッシュされないっていうことができるので、どこからどこまでのキャッシュを更新するのかみたいな細かい制御ができない。 |
| refetch |確実に該当データのキャッシュを無効化することができる。無効化というか再フェッチになるので、物理的に再生成させることができる。特に上のアップデート、ドキュメントキャッシュの場合は、キャッシュをリセットさせたいけど、場合によってはできない場合があると思います。例えば削除更新をしたときにタイプネームをレスポンスに含めてない場合などもあると思うので、そういった場合にも強制的にキャッシュをクリアすることができる。クリアというかデータを再生成することができる。 |リフェッチをフロント側で実装するという手間がかかる。またクエリを2回実行することになる。 |
| 手動キャッシュ操作 |即座にキャッシュを更新することになるので、そのキャッシュを参照するような処理がある場合はパフォーマンスの改善が見られる。いわゆる楽観的更新みたいな感じで、とりあえずユーザーのソースに連動して画面がそれに従って表示されるっていうユーザー体験を優先することができる。 |サーバー側で処理が失敗した場合に、その整合性を維持するためにクライアントでロールバック処理をしなければいけない。そういうことをしないと、サーバー側とクライアント側で整合性が取れない状況が生まれてしまう。 |

### ケースごとの適切な戦略

- **書籍の編集（title を変更）**:
こちらは戦略3を使って即座にキャッシュを更新するやり方で、UXの体験を向上させるのが良いかと思います。理由としては、サーバー側とクライアント側のずれが生じたとしてもそこまでダメージはないっていうのと、楽観的更新の仕組みを整えてロールバックする仕組みを作れば、そこまでユーザー体験を損なうことはないかなという、万が一の障害におけるダメージがそこまで大きくないっていうので、UXを優先した方が良いという考えで、戦略3で良いかなと思います。

こちらは戦略1を利用すれば良いと思います。つまり、デフォルトのキャッシュ管理で事足りるかなと思います。具体的な流れを説明すると、タイプネームとIDで更新すべきキャッシュを1位に特定できるので、サーバーの処理が終わった後にキャッシュも更新すれば良いからです。
- **書籍の新規追加**:
新規追加の場合は、基本的にクライアントとサーバーの整合性っていうのを合わせた方がいいんで、戦略1か戦略2になるんですけど、2よりは1の方が実装がシンプルになるかなと思うので、戦略1を採用します。戦略3を取らなかった理由としては、クライアントとサーバーの整合性が取れないとダメージがでかいかなと思います。なんでかっていうと、整合性が取れない状態で例えば本の詳細を開いたりだとか、本に対する何らかのアクセス操作をされた場合にシステムエラーが多発することが考えられるからです。なので、何かバックで処理が失敗した場合は、もう即座にキャッシュを更新するとかじゃなく、システムエラーにしてクライアントにはそれを通知するっていう風な設計にした方が安全かなと思ってます。

こちらの場合は手動でキャッシュ操作をする必要が出てくるかと思います。リソースがクリエイトされた場合は、そのリソース自体単体でキャッシュに保存されますが、例えば一覧ページのキャッシュには多分何もしないと追加されないと思うので、リストを管理しているキャッシュに対して手動でキャッシュを追加する必要があるかなと考えることができます。
- **書籍の削除**:
戦略1で新規追加と同じ理由ですね。

こちらも新規追加と同じ原理で、削除したリソースのキャッシュだけでなく、関連するキャッシュリソースに対してキャッシュを削除するという指示を与えなければいけません。原理的にやろうと思えば自動でできるんですが、urql はあえてそういった挙動をしてません。何でかっていうと、それを実現しようとすると「どこのキャッシュは残して、どこのキャッシュは消すのか」みたいな判断ができないからです。それは要件に絡むものなので、そのキャッシュの機構が勝手に判断していいものではないからです。



### 新規追加と削除がなぜ編集より難しいか

リソースの追加と削除っていうのは、すでに存在するキャッシュ領域の中で、どこに追加するのか、追加すべきなのかっていうのが要件に絡んでくるから、自動化することが難しいため、編集より難しいものかなと考えています。編集の場合は確定で、全てのキャッシュ領域に存在する該当データを更新する必要があると思います。キャッシュからどこからどこまで更新するのかという判断が、新規追加と削除の場合は難しいから、編集より難しいというふうに考えています。

### 📝 レビュー（Q3 修正後）

修正された回答は本質を正確に捉えています。

**正確に理解できているポイント:**

- **編集（戦略1）**: `__typename` + `id` で対象を一意に特定できるので、urql の自動更新に任せられる
- **新規追加（手動キャッシュ操作）**: 作成されたリソース単体はキャッシュに保存されるが、リスト系クエリへの追加は手動で指示する必要がある
- **削除（手動キャッシュ操作）**: 「原理的にやろうと思えばできるが、urqlはあえてやらない」という設計判断を正しく理解している。要件（論理削除、削除済みタブへの移動、ページネーション補充等）に依存するため、機構が勝手に判断すべきではない

**新規追加と削除が編集より難しい理由の総括:**

- **編集**: エンティティ内部の値変更 → 参照先の値が変わるだけで、リストの構造は不変
- **追加・削除**: リストの構造そのものが変化 → 「どのリストに属すべきか」の判断が必要

この構造変化 vs 値変化の違いが本質です。

**実務での補足 — `@urql/exchange-graphcache` の `updates`:**

urqlで追加・削除の手動キャッシュ操作を宣言的に書きたい場合、`@urql/exchange-graphcache` を使います。以下のように、Mutationごとにキャッシュ更新ルールを定義できます：

```ts
import { cacheExchange } from '@urql/exchange-graphcache';

const cache = cacheExchange({
  updates: {
    Mutation: {
      createBook: (result, args, cache) => {
        cache.updateQuery({ query: BooksQuery }, (data) => {
          data.books.push(result.createBook);
          return data;
        });
      },
      deleteBook: (result, args, cache) => {
        cache.updateQuery({ query: BooksQuery }, (data) => {
          data.books = data.books.filter((b) => b.id !== args.id);
          return data;
        });
      },
    },
  },
});
```

現在のプロジェクトでは標準の `cacheExchange`（Document Cache）を使っていますが、実務ではこの Graphcache に差し替えるケースが多いです。internal-system の BFF もおそらくこちらを採用することになるので、実装演習では一旦 `reexecuteQuery` による refetch で簡単に済ませ、Layer 2 以降で Graphcache に移行することを検討しましょう。
