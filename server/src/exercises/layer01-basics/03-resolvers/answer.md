# 演習1-3: Resolver の仕組み — 言語化回答

## Q1: REST Controller と GraphQL Resolver の違い

### フィールドごとにResolverを分ける設計がなぜ必要か

フィールドごとにリゾルバを設けることによって、それらのフィールドを取得するか否かであったり、取得の仕方を柔軟に変更できるようにするためです。例えばRESTではすべての項目を返すことになるが、GraphQLの場合はすべての項目ごとにリゾルバーが存在するので、場合によってはそのフィールドを返却値に含めないこともできるし、含める場合その項目の取得方法をカスタマイズすることができるようになる。

また、責務の分散という観点から見ても、各フィールドごとにリゾルバを設けることによって、異なるデータソースからデータを取ってくるとしても、それぞれをまとめるだけで良いことになるので、リゾルバー自体がどこからデータを取ってくるかっていうのを意識しないで、その各フィールドが呼び出した結果だけをモデルに統合するっていう責務だけに集中することができるという点で、RESTよりは責務の分離がしっかりできるかなと思います。もしこれをRESTでやろうとすると、おそらくコントローラー内に各データソースからの取得ロジックなどを呼び出すことになるかと思います。なので各項目を束ねるという責務以外のことをRESTのコントローラーでやってしまうことになるので、そういう責務の分離ができない状態になってしまうのに比べて、GraphQLのリゾルバーは各フィールドごとに責務があるというふうに言えるので、そういった責務の分離がしやすいのかなと思います。

### REST Controllerでリレーション先のデータをどう返すか、その課題

基本的には1対1で紐づいているレスポンスをどんな時でも返すようになります。そのため、クライアント側で必要じゃない項目までも取ってきてしまうというオーバーフェッチの問題があります。また逆に、必要な項目を取ってくるために何回も別のエンドポイントを叩く必要が出てきてしまうため、結果的に画面でAPIを呼び出す回数が多くなってしまいます。

### GraphQLのフィールドリゾルバーがその課題をどう解決するか

FieldResolverがあることで、その項目を返すか返さないかっていうのを柔軟に変更ができるし、上記の再説明になるんですけども、どういうふうに取ってくるのかっていうのをカスタムすることができます。

### 📝 レビュー（Q1）

3つの観点は押さえられていますが、もう少し深掘りできるポイントがあります。

**1点目 — REST Controllerの課題についての補足:**
「オーバーフェッチ」と「N回呼び出し（アンダーフェッチ）」の両方に触れている点は良いです。ただし、RESTでリレーション先を扱う方法はもう1つあります — **JOINして1つのレスポンスに含める**パターンです。例えば `/books?include=author` のようにクエリパラメータで展開を指定する設計や、レスポンスに最初から `author` を埋め込む設計です。

このアプローチの問題点は何だと思いますか？ — 例えば、書籍一覧画面では著者名だけ欲しいけど、書籍詳細画面では著者のプロフィールも欲しい、というケースを想像してみてください。サーバー側で「常に著者情報を含める」設計だと、どんな問題が起きそうですか？

その場合は書籍一覧画面でも著者の情報を返してしまうようになるため、不必要な情報をレスポンスに含めてしまうことになります。よって本来であれば少ない情報で返せるのに、無駄にジョインすることによってパフォーマンスの低下を招いてしまいます。

**2点目 — フィールドリゾルバーの本質:**
「取得方法をカスタムできる」という説明は正しいですが、フィールドリゾルバーの最大の強みは **「データソースを自由に分離できる」** 点です。例えば `Book.author` はDB、`Book.coverImage` はS3、`Book.averageRating` は外部レビューAPI、といったように **異なるデータソースから取得するフィールドを、1つのBookオブジェクトとしてクライアントに返せる** のがGraphQLの本質的な強みです。

RESTで同じことをやろうとしたら、Controller内でDB・S3・外部APIを全部呼んで結合する必要があり、責務が肥大化します。一方GraphQLなら、各フィールドリゾルバーが独立して自分の担当ソースから取ってくるだけです。

→ この「責務の分散」と「データソースの分離」の観点を踏まえて、Q1の回答を補強できそうですか？（answer.mdに追記してもOK、頭の中で理解できればOKです）

## Q2: N+1問題

### 書籍10冊の場合、DBクエリは合計何回か

Booksで1回のクエリが必要で、さらにその中のオーサーを各ブックごとに解決しなければいけないので、それが10回解決されるので、11回のクエリになります。

### なぜ「N+1問題」と呼ばれるか（1とNの意味）

何かしらのリストを取得するクエリにおいて、各リストの要素に対しても個別にクエリを実行しなければいけない場合、リストのサイズをNとすると、全体のリスト取得で1、プラス個々のリストのアイテムに対してクエリを実行するので、N回のクエリが発生するというパフォーマンスの問題にちなんで、結局Nプラス1回のクエリが発生するから、Nプラス1問題というふうに言われています。

### REST APIでの対処法と、GraphQLで同じアプローチが取りにくい理由

おそらくRESTの場合は、リストに紐づくアイテムをまとめて取ってくるときは、結合、ジョインをするんだと思いますが、GraphQLではジョインをすることが構造上難しい設計になっています。Q1のデメリットになる部分であって、フィールドごとに独立してデータソースから取得してくる。必要になったときにそのフィールド専用の取り方をできるというような柔軟性を維持している分、それ逆に言うとデータを取得するときにならないと何を取得していいのかが分からないというような状態になり前もってジョインするっていうことが難しい設計になってます。あとはRESTだったら、もうAPI作ってる段階でジョインするっていうのは確定してるので、それでいいんですけども、GraphQLの場合は、クライアントが何を取ってくるのかっていうのを決めるので、そのクエリがジョインが必要なのか、必要じゃないのかっていうのが判断ができないため、ジョインというアプローチが取れない。からNプラス1問題というようにそのフィールドが個別にデータを取ってくる。それがリストだった場合、そのリストの要素分フィールドのリゾルバーが機能するっていう感じになってます。

### 📝 レビュー（Q2）

3つの観点すべてに対して正確な回答です。特にGraphQLでJOINが取りにくい理由を「クライアントが何を取るか決めるため、事前にJOINの必要性を判断できない」と説明できているのは本質を捉えています。

**補足 — Q1との繋がり:**
Q1でフィールドリゾルバーの強みとして「データソースを自由に分離できる」と学びましたが、N+1問題はまさにその**代償**です。「各フィールドが独立してデータを取る」という設計を貫いた結果、リレーション解決時にまとめて取れなくなる。柔軟性とパフォーマンスのトレードオフですね。

**解決策の方向性（Layer 2 で詳しく扱います）:**
この問題を解決する代表的な方法が **DataLoader** です。DataLoaderは「同じイベントループ内で発生した複数のfindOne呼び出しを1つのfindManyにまとめる」という仕組みで、GraphQLの柔軟性を保ったままN+1問題を解消します。

例えば今回の例だと、`author`フィールドが10回呼ばれても、DataLoaderが10個のauthorIdを集めて `findByIds([1, 2, 3, ...])` という1回のクエリにまとめてくれます。結果、DBへのクエリは合計2回（books 1回 + authors 1回）で済みます。

→ この「同じ関数呼び出しをバッチにまとめる」という仕組みがなぜ可能なのか、Layer 2で体験してもらいます。

Q2完了です。Q3に進みましょう。

## Q3: @ResolveField の実行タイミング

### クエリA / クエリB それぞれで @ResolveField は呼ばれるか

QA はオーサーのリゾルバーが呼ばれます。対して QB はオーサーのリゾルバーは呼ばれません。

### 遅延解決（Lazy Resolution）と呼ばれる理由

上記のクエリAとクエリBで見たように、ResolveFieldというのは、必要になったときにフィールドリゾルバーを実行するという挙動がわかる。RESTのように即座に実行するのではなく、必要になったたびに遅延して取得してくるという、意思決定が遅延するというニュアンスから遅延解決というふうに呼ばれたんじゃないかなと思います。意思決定という観点でいうと、Eager loadingの場合はもうそのエンドポイントが呼び出された時点で確定してるんですけども、GraphQLのResolveFieldの場合は、クライアントからどういった呼び出しがされたかというのを読み取って、何を書いたのかが決まるという意味で、この取得項目の決定が遅延しているというふうに捉えることもできると思います。

### RESTで同じ効率を実現しようとしたらどうなるか

もし、この遅延解決を REST で実現するとしたら、どういう設計が考えられますかね？一つのエンドポイントを呼び出して、そのレスポンスを柔軟に差し替えるような形になると、おそらくリクエストパラメーターかボディーか何かで、取得したい項目みたいなのを別途用意する必要があって、その項目に一致するものだけ書き集めてくるみたいな挙動になると思うんですが、でも結局内部的には Eager ローディングして、そこからデータを抽出して返すみたいなことをするので、データアクセス的には変わらないんですよね。なんで、そもそもエンドポイントをめっちゃ大量に柔軟に用意するみたいな、柔軟に用意するっていうか、ユースケースごとに用意するみたいな思想になりそうな気がしますが。

### 📝 レビュー（Q3）

3観点とも的確です。

**遅延解決の理解について:**
「取得項目の決定が遅延している」という説明は本質を突いています。Eager loading は「API設計時に取得内容が確定」、GraphQLのResolveFieldは「クエリ受信時に取得内容が確定」という対比が分かりやすいです。

**RESTで同じ効率を実現する場合の考察について:**
よく考えられています。実際にRESTで類似のアプローチを試みた例をいくつか紹介しておきます：

1. **フィールド選択パラメータ**（例: `/books?fields=title,author`）— まさに回答で触れた方式。GitHubのREST APIやGoogleのAPIなどで採用されていますが、指摘通り内部的にはJOINして抽出するだけなので、DBアクセスの効率は上がりません
2. **ユースケース別エンドポイント**（例: `/books/list`, `/books/detail`, `/books/with-author`）— BFFパターンでよく見られます。フロントエンドの画面ごとに専用のエンドポイントを作る方式で、データ転送量は最適化できますが、エンドポイントが爆発的に増えるメンテナンスコストが問題になります
3. **Sparse Fieldsets**（JSON:API仕様）— フィールド選択の標準化仕様。これもDBアクセス側の効率化には直結しません

つまりRESTでどう頑張っても、**「クエリのたびに動的に取得フィールドを決めつつ、かつ必要なデータソースだけを叩く」**という両立は構造的に難しいです。GraphQLのフィールドリゾルバーは、スキーマとランタイムのクエリ解析が密結合しているからこそ実現できる設計と言えます。
