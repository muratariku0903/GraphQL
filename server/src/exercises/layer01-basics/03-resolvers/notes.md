# 演習1-3: Resolver の仕組み — 学び・気づきのログ



```
query {
  books {
    id
    title
    author {
      name
    }
  }
}
```
上記のクエリを実行した結果、以下のログが吐き出された。この結果からフィールドリゾルバーが3回実行されていることがわかる。よって1回のクエリでN+1回の呼び出しが実行されていることがわかる。
GraphQL Playground: http://localhost:3002/graphql
execute fineOne a1
execute fineOne a2
execute fineOne a3

また、同じ著者を持つ複数のブックスが存在する場合も、同じ著者に対するfindOneが実行されている。

### 📝 実装レビュー

**実装の評価: 良好**

すべての課題が正しく実装されています。

**良い点:**
- **`@HideField()` の活用**: `authorId` をGraphQLスキーマから隠しつつ、TypeScriptの型としては残しているのは適切な設計。演習で触れた「内部用フィールド」の実装パターンが正しく理解できています
- **`@ResolveField` と `@Parent` の使い方**: 正しく親オブジェクト（Book）を受け取り、`authorId` で著者を解決できています
- **DIの拡張**: `BooksResolver` のコンストラクタに `AuthorService` を追加し、`BooksModule` にも providers として登録。モジュールシステムの理解が深まっています
- **サンプルデータ**: 書籍4冊のうち2冊を同じ著者（a2）にしているのは良い工夫。N+1問題の観察において「同じ著者が重複取得される」ことを確認するための設計意図が感じられます

**N+1問題の観察結果について:**

notes.md の観察結果は正確です。

```
execute fineOne a1
execute fineOne a2
execute fineOne a3
execute fineOne a2   ← 同じ著者が重複取得されている
```

→ 書籍4冊に対して `findOne` が4回呼ばれており、**1回のbooksクエリ + 4回のauthorクエリ = 5回のデータアクセス（N+1問題）** が発生しています。

さらに注目すべきは **`a2` が2回取得されている** 点です。同じ著者に対して同じクエリを2回実行しているのは純粋に無駄です。これは**キャッシュによる重複排除**で解決できるポイントでもあり、DataLoaderの設計思想（バッチ化 + キャッシュ）に繋がります。

**Layer 2で学ぶDataLoaderを使うと、上記のログは以下のようになります:**
```
execute findMany [a1, a2, a3, a2]  ← 1回にまとめる
// さらにキャッシュで重複排除するので、実際のDBクエリは [a1, a2, a3] の1回
```

この違いを実感するためには、まず今回のようにN+1問題の痛みを体験しておくことが大事です。いい学びになりました。
