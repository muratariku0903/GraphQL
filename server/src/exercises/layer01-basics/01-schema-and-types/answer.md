# 演習1-1: スキーマと型システム — 言語化回答

## Q1: GraphQLの型システムとTypeScriptの型システム

### GraphQL → TypeScript の対応表

| GraphQL | TypeScript | 補足 |
|---------|-----------|------|
| Scalar (String, Int, Float, Boolean, ID) | Stringとbooleanに関してはTypeScriptとほぼ同じです。ただintとfloatで分かれているところがTypeScriptの場合はnumberという型で一本化されています。idと対比する型というのはTypeScriptには存在せず、普通にstring型として扱います。 | |
| Object | TypeScriptはインターフェースという型を使ってオブジェクトの型を表現します。ここのインターフェースの項目の型はそれぞれマスカラだったり、オブジェクト型を入れ子にしたりというのが同様にできます。 |デフォルトとしての挙動が両者の間で若干異なっていて、GraphQLの場合は何もしなければnullになりますが、TypeScriptの場合は何もしない場合はnon-nullになります。なので、デフォルトにしたときのnullを許容するかしないかという点で異なります。 |
| Enum | TypeScriptにもenumという型が存在します。またUnion型でも表現することができます。 |TypeScriptの場合はコンパイル時に型のチェックを実施するのに対し、GraphQLはコンパイル時に加えて実行時にもバリデーションチェックをします。なので、実行した時に不正な値が入っていたらそこでエラーになります。 |
| Input | TypeScriptの場合は、入力と型っていうのがそもそも分かれていません。入力側と出力側に対して同じ型を適用することができます。なので、Inputという独立した型は用意されていません。 | GraphQLはサーバーに渡す方とサーバーから返ってくる方を明確に責務を分離しています。理由としては、まずインプット側、何点かあるんですけど、まず安全性の観点でいうと、インプット側には循環参照ができないという制約も受けています。循環参照できちゃうと、無限にネストしたリクエストをサーバーに送ることができちゃうので、それはドスコイトウォーキーの温床になります。これを使用レベルでGraphQLは対策しようと考えていて、そのためにクライアントから渡すものは中間最初ダメにして、サーバーから返ってくるものはOKにするという、責務の分離をすることによって解決しています。続いてが、責務の分離という観点でいうと、そもそも同じ型を使い回せてしまうと、その型がクライアントが転送するものなのか、それともサーバーから送られてくるものなのかという判別がつかない状態になると思います。そうするとその型の一部の項目はサーバーから返ってくる場合もあるし、もしくはその逆でクライアントからしか値を設定しない項目も中には出てくると思うので、そういったものを共通として利用してしまうと、用途の判断が難しくなってしまうので、GraphQLの場合は入力の型と出力の型を明確に分離しています。 |
| Interface |こちらTypeScriptでも同じくインターフェースというものが存在します。 | |
| Union |同じくユニオンも存在します | |

### ObjectとInputが分離されている理由

上の対応表でも説明したんですけども、一つは安全性というところで、循環参照のリクエストを排除するためです。要するにリクエストの方とレスポンスの方を分けることで、どちらかにルールを適用することができますよね。リクエストにはこういう制約も受けて、レスポンスにはこういう制約も受けて、みたいなそれの細かく制御できるっていうのが根本的なメリットとしてあって、GraphQLの場合はリクエストでは循環参照っていうDOS攻撃ができちゃうので、それを防ぐためにリクエストのほう、いわゆるインプットにはそれができないような仕組み、制約も受けています。ResponseではそれはResolverが制御できるので、そこの制約は特に設けてない状態です。というのがセキュリティというか安全性の観点です。

もう一つが責務の分離ということで、こちらも上で説明した通り、何か一つの方というのを入力と出力で共通で扱ってしまうと、それは一見便利なようにも見えるんですが、その型の本当のユースケースみたいなのが曖昧になってしまうと思います。これが曖昧になると、その型を本当にそこで使っていいのかどうなのかっていうのがなかなか判断しづらい状況になってしまうので、メンテナンス性の低下を引き起こす要因になってしまうかなと思います。そういった運用面の観点から、GraphQLでは入力と出力という責務を明確に分離しています。

### 📝 レビュー（Q1）

全体的に的確な回答です。特にInput/Object分離の理由を「セキュリティ（循環参照によるDoS防止）」と「責務の分離（メンテナンス性）」の2軸で説明できているのは良いです。

**対応表について補足:**
- Scalar / Enum / Input の説明は正確です。GraphQLのEnum が「実行時バリデーションも行う」という点に気づけているのは鋭い観点です。
- Object型の「GraphQLはデフォルトnullable、TypeScriptはデフォルトnon-null」という違いの指摘も重要です。これはGraphQLが **部分エラー（partial failure）** を許容する設計思想から来ています — あるフィールドの解決に失敗しても、他のフィールドは返せるようにするためです。

**1点深掘り質問:**
Input/Objectの分離理由として、もう1つ実務的に大きい理由があります。例えば `Book` 型の `id` フィールドはサーバーが自動生成しますよね。この場合、`CreateBookInput` に `id` は含めるべきでしょうか？ — この「入力と出力でフィールド構成が異なる」という点も、分離の動機として考えてみてください。

サーバー固有のフィールドはインプットには含めるべきではないですね。こうすることによって、サーバーが本来生成するようなフィールドをクライアントから送りつけるといった改ざんを未然に防ぐことができるようになっているかと思います。

→ その通りです。`id`, `createdAt`, `updatedAt` のようなサーバー管理フィールドを入力から除外できるのが、Object/Input分離の実務上最大の理由ですね。Q1は完了です。

## Q2: なぜGraphQLは「スキーマファースト」なのか

### フロントエンドとバックエンドの並行開発への貢献

GraphQLではまずスキーマを最初に定義してから、そのスキーマをもとにフロントエンドとバックエンドが並列して開発を進めることが可能になっています。フロントが何が欲しいのか、フロントから何を渡すのか、バックエンドから何を与えるのか、受け取るのかっていうのは、このスキーマっていう共通の契約書みたいなのを守るようにGraphQLではなるので、仮にそれを破ってしまった場合はエラーなどで弾かれるように実装レベルでそういった制約をスキーマを通して定義できるので、両者が並列して開発することができます。

### スキーマが存在しないREST APIで起きがちな問題

RESTの場合は様々な問題が発生するんですけども一つとしての並行開発っていうのが難しいっていうのはあると思いますQ2の一番最初のフロントエンドとバックエンドの並行開発っていうのがあるんですけどもRESTの場合はバックエンドっていうのを先に開発してそのレスポンスインターフェースを見てフロントが良しないように調整していくっていう流れになると思うので例えばバックエンドの開発が遅れた場合そのシェアがフロントに寄ってしまうというような開発の方向性に影響を与えてしまうっていうのがあるかと思いますまたAPIの使用書と実装というのが密につながっていないためそれらがずれてしまうということが構造的に起こり得ると思いますオープンAIなどのAPIの使用書を作成するツールなどは用意されていますがそれは必ずともコードと結びついているものではなく手動で開発者が作成するものになるので実装と仕様が分離するということは普通に起こり得るかなと思いますまたバリデーションというか型のエラーなどの検知力というのも弱くて、RESTの場合はAPIごとにバリデーションを定義しなきゃいけないと思うんですけども、それだと、 場合によっては使用者のバリデーションとずれてしまうというヒューマンエラーみたいなのが発生するケースもあるかと思います

### 📝 レビュー（Q2）

良い回答です。3つの論点（並行開発の困難さ、仕様と実装の乖離、バリデーションの弱さ）をしっかり挙げられています。

**並行開発への貢献** — 「スキーマ＝共通の契約書」という表現は的確です。補足すると、スキーマが先にあることで、フロントエンドはバックエンドの実装完了を待たずに **モックデータでUIを作り始められる** という点も大きいです。GraphQLにはイントロスペクション機能があるため、スキーマさえ定義されていればツール（GraphQL Code Generator等）が型定義やモッククライアントを自動生成でき、フロント側の開発がすぐ始められます。

**REST APIの問題** — OpenAPIに触れている点は良いですね。まさにOpenAPI/Swaggerは「後付けのスキーマ」であり、コードと自動的に同期する保証がありません。一方GraphQLのスキーマはランタイムそのものが解釈するので、スキーマと実装が乖離すること自体が不可能（起動時にエラーになる）という構造的な強さがあります。

Q2完了です。Q3に進みましょう。

## Q3: Code First vs Schema First

### それぞれのメリット・デメリット

| | Code First | Schema First |
|---|-----------|-------------|
| メリット |コードがそのままスキーマになるので、クラスなどの型定義を書くだけでスキーマと同期が取れること。つまりコードを書くだけでスキーマの一元管理ができる。 |隙間を先に定義できるので、バックエンドの開発以外の方たちにもそれを早めに共有できるし、その先の作業も並行でやりやすくなる。 |
| デメリット |スキーマを理解するためには多少バックエンドのクラスの実装などにも目を通さないといけないので、技術的なコストがかかる、認知コストっていうのがかかる。 |スキーマとコードが分離されているので、SDLを書いてその後それに沿ったクラス定義などをしなければいけないということで、スキーマとコードを二重管理する必要が出てくる。 |

### どのようなプロジェクトでどちらを選ぶべきか

要するにどっちも良いところと悪いところがあるというので、プロジェクトの方向性で取捨選択すればいいのかなというふうに思っていて、Code Firstの場合はバックエンド主体の開発プロジェクトに向いているかなと思います。そもそもいろいろな都合でバックエンドから開発しなきゃいけないというようなところであったり、バックエンドの開発を優先的に行いたいプロジェクトの場合はCode Firstでいいかなと思うんですけども、一方でフロントとバックエンドを並列で進めたいとか、スキーマについて各チームで議論をしたいみたいなところの場合は、まずはスキーマファーストでやるのがいいかなと思ってます。

### 📝 レビュー（Q3）

メリット・デメリットの対比、判断基準ともに良い整理です。「Code First＝一元管理だが認知コスト」「Schema First＝共有しやすいが二重管理」という対比は正確です。

**補足:**

実は Code First でも並行開発は可能です。Code First で生成される `schema.gql`（`autoSchemaFile` で出力されるファイル）をGitにコミットしておけば、フロントエンドはそのファイルを見てGraphQL Code Generatorで型を生成できます。つまり **Code Firstでも成果物としてのスキーマは共有できる** ので、「並行開発＝Schema First一択」というわけではありません。

実務での判断基準をもう少し整理すると：
- **Code First が向くケース**: NestJS/TypeScriptチーム、型安全性を重視、既存のGraphQLスキーマがない新規開発
- **Schema First が向くケース**: 複数言語のバックエンド（Go + Node等）、既存の `.graphql` スキーマがある、非エンジニア（デザイナー等）もスキーマを読む

internal-system の BFF 層は NestJS + TypeScript の Code First を採用していますが、それはまさに上記の「NestJSチーム＋新規開発」に該当するからです。
