# 演習1-1: スキーマと型システム — 学び・気づきのログ

今回はクエリの処理を2つ定義して、それぞれで動作確認しました。1つ目のクエリはインプットパラメータなしで全部取ってくるやつと、2つ目がインプットパラメータありでIDに絞り込むものになりますね。いずれも取得する項目を呼び出し元で選べるようになっていて、例えばBooksだった場合はタイトルだけ指定した場合はタイトルだけ取ってくれるようになってますね。これはREST APIではない性質ですね。REST APIの場合だったらそれ用のエンドポイントも1個用意しなきゃいけないんですけど、GraphQLの場合は、一つのエンドポイントで様々なデータの取り出し方があるなと思いました。

NestJSを実行すると自動でスキーマファイルが生成されていて、そこを見るとモデルファイルで定義したブッククラスとenum、そしてサービス層で実装したインターフェースですね。今回の場合は先ほど述べたBooksとBookFoo、この2つのインターフェースが定義されています。なのでコードからスキーマファイルというのが自動生成されたということが確認できました。

### 📝 実装レビュー

**実装の評価: 良好**

3ファイルとも適切に実装されています。

**良い点:**
- **Resolver / Service の責務分離**が正しくできている。Resolverはデータ変換のみ、データ操作はServiceに集約
- `@Field(() => ID)`, `@Field(() => Int, { nullable: true })` など、GraphQLの型指定が正確
- `registerEnumType()` による Enum 登録も正しい
- `findOne` の戻り値を `Book | null` にして、`nullable: true` でnullを返せるようにしている点も適切
- 自動生成された `schema.gql` で `publishedYear: Int`（`!` なし＝nullable）になっていることが確認できる

**1点改善ポイント:**
- `publishedYear` のプロパティ定義が `publishedYear!: number | null` となっていますが、`!`（definite assignment assertion）と `| null` の組み合わせは少し不自然です。`publishedYear?: number | null` か `publishedYear: number | null` の方が意図が明確になります。ただし動作には影響しません。

**観察ポイントへの回答について:**
notes.md で「取得する項目を呼び出し元で選べる」「REST APIの場合はそれ用のエンドポイントを用意しなければならない」と書いているのは正しい観察です。もう1つ気にしてほしいのは、 **`books { title }` でも `books { title author publishedYear genre }` でもサーバー側の `findAll()` は全フィールドを返している** という点です。フィールドの絞り込みはGraphQLのレイヤーが行っており、Resolverは常に全データを返しています。つまりサーバー側の処理量は変わりません。この点はLayer 2のN+1問題と `@ResolveField` で重要になります。
