# 演習1-2: Query と Mutation — 言語化回答

## Q1: なぜ Query と Mutation を区別するのか

### 実行の意味論（セマンティクス）

クエリとミューテーションを区別することで、その処理が副作用を持つか持たないかというのを使用レベルで制限することができます。もしクエリとミューテーションの区別をせずにごっちゃにしてしまうと、例えば何かしらのGETリクエストに相当するもので副作用を発生させてしまったり、という問題がありますが、GraphQLの場合、そこを明確に分離し、クエリの処理では副作用を発生させることができないという仕様があります。そういった意味で、クエリとミューテーションを区別することで、それが副作用を持つものなのかそうじゃないのかっていうのを安全に処理することができます。

### 並列実行 vs 直列実行

データを取ってくる処理と何かしらのミューテーションをする処理において、基本的にデータを取ってくる処理というのは副作用がないので同時並行で実行しても問題ないのですが、ミューテーションの場合はデータベースの内容を書き換えるということが発生するため、実行する順序というのがとても大事になります。例えば、ユーザーを作成してユーザーを削除するという2つのミューテーションがあったときに、削除するという処理を先にできないじゃないですか。なので、ミューテーション処理というのは実行の順番というのは大事になるので、直列で実行する必要があります。

### キャッシュへの影響

クエリの結果をキャッシュしますが、ミューテーションが発生した後は、ミューテーションで返ってきた値でキャッシュを更新しようとしてくれます。ただ単発の値であればキャッシュのマッピング構造から該当するものを直接書き換えるといったことができるんですが、リスト構造などの場合はなかなかそれが構造的に難しいようになっています。これはキャッシュの構造の問題です。なので、リスト構造のキャッシュをミューテーション後にリフレッシュしたい場合は、別途ユーザーがプログラムで宣言する必要が出てきます。

### 📝 レビュー（Q1）

3つの観点すべてに対して的確に回答できています。

**セマンティクスについて** — 「副作用の有無を仕様レベルで制限する」は正しいです。ただ1点補足すると、GraphQLの仕様はQuery内での副作用を**技術的に禁止しているわけではありません**。あくまで「Queryは副作用を持たないべき」という**規約（convention）**です。RESTでも `GET` で副作用を起こすことは技術的に可能だが「すべきでない」のと同じ構図ですね。

**並列/直列について** — 「ユーザー作成→削除の順序が重要」という具体例が分かりやすいです。完璧です。

**キャッシュについて** — urqlの正規化キャッシュの挙動をよく理解しています。「単発の値は `__typename` + `id` でキャッシュを直接更新できるが、リストは追加/削除の反映が難しい」という点は、実装演習でも実感できるポイントです。

Q1完了です。Q2に進みましょう。

## Q2: InputType の設計原則

### パターンA（共通）vs パターンB（分離）のどちらが良いか

パターンBの分離型の方が優れているかなと思います。パターンAの場合は、publish以外の項目が全部必須項目になっているかと思います。なので、この場合、createの場合はいいんですけど、updateするときに部分的に更新するユースケースに対応することが難しいかなと思います。できるっちゃできるんですけど、すべての項目を渡さなきゃいけない。変更がない項目に関しても送らなきゃいけないという点で、不要なリクエストが発生するかなと思います。対してBの場合は、createは全部必須で、updateは任意というふうになっているので、必要最小限の更新で済むように最適化されています。

### Updateで全フィールドを必須にすると何が困るか

上記で説明している通り、アップデートは部分的に項目を更新するケースというのも考えられると思うので、全部の項目を必須にしてしまうと、変更が入らなかった項目もリクエストに含める必要があるので、不必要なデータの通信が発生してしまいます。

### 📝 レビュー（Q2）

パターンBが適切であるという判断とその理由は正しいです。

補足として、通信コストに加えてもう1つ重要な問題があります。Updateで全フィールド必須の場合、クライアントは更新前の値を**事前に取得しておかないと**リクエストを組み立てられません。例えば `title` だけ変えたくても、`author` や `genre` の現在の値を知っている必要がある — つまり**余分なQueryが1回発生する**か、クライアント側でローカル状態を常に保持し続ける必要があります。これは実装の複雑さにも直結します。

また、全フィールド必須だと**意図しない上書き**のリスクもあります。古いデータを持ったクライアントが更新リクエストを送ると、別のクライアントが先に変更した内容を上書きしてしまう可能性が高まります（楽観的並行制御の問題）。

Q2完了です。Q3に進みましょう。

## Q3: Mutationのレスポンス設計

| パターン | メリット | デメリット |
|---------|---------|-----------|
| Boolean（成功/失敗のみ） |APIの実装はシンプルになります。失敗したときにtrue、成功したときにtrue、失敗したときにfalseだけを返せばいいので、簡易的な実装のときには向いているかなと思います。 |更新後のデータを使ったクライアントのリフレッシュなどには対応できないかなと思います。例えばキャッシュの値を更新後の値で最新化するといったようなユースケースを満たすことができない。 |
| 変更後のオブジェクト（例: Book） |ブーリアのデメリットを解消しているのがメリットかなと思います。更新後の値を使ってクライアント側で何かしらリフレッシュ処理をするといったケースを実現できます。 |こちらは更新後の値を API 側で取得して返すというひと手間が必要になります。 |
| 専用レスポンス型（例: DeleteBookResult） | API の返却値っていうのをクライアントの挙動に最適化することができるので、より柔軟に API とクライアントの連動が満たせるかなというふうに思います。例えばオブジェクトにサクセスっていうブーリアンを入れたり、あとは変更後のオブジェクト自体を入れることもできますし、エラーが発生した場合はエラーメッセージを持ってくるみたいなことができるので、そうするとクライアント側はそのリザルトを使ってそれをただ表示するだけみたいなシンプルな挙動が実現できるかなと思います。 |こういったカスタムリザルトっていうのは横展開する必要があるので、何かしら開発者に共有する必要が出てくるかなと思います。あるいは実装するときにそういった制約を型システムレベルで設定してあげるという、そういった環境づくりのコースが必要になってくるかなと思います。 |

### 📝 レビュー（Q3）

3パターンの整理が的確です。特にパターン3の「クライアント側はリザルトをただ表示するだけ」という表現は、GraphQLのレスポンス設計の本質をよく捉えています。

**補足 — キャッシュとの関連:**
パターン2（変更後のオブジェクトを返す）が実務で最も多用されるのは、まさにQ1のキャッシュの話と繋がっています。urqlやApollo Clientは `__typename` + `id` でキャッシュを正規化しているため、Mutationが変更後のオブジェクト（idを含む）を返せば、**該当エンティティのキャッシュが自動で更新されます**。Booleanだけ返すとこの恩恵が受けられません。

**パターン3が特に活きるケース:**
削除操作では「削除されたオブジェクト」を返しても意味が薄いので、`{ success, deletedId }` のような専用型が有効です。また、Layer 4で学ぶ **Union型を使ったResult型パターン**（`union CreateBookResult = Book | ValidationError`）は、パターン3の進化形として非常に強力です。
