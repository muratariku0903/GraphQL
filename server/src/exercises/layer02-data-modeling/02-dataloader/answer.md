# 演習2-2: DataLoader によるN+1問題の解消 — 言語化回答

## Q1: DataLoader のバッチ処理の仕組み

### 「まとめる」処理のタイミング

GraphQLのリクエストをResolverが処理するタイミングで、それぞれ同じデータソースに対する処理をまとめて格納していく感じになります。まとめ処理のタイミングとしては、一番最初の大元を取得した直後になります。

補足すると、同期処理というのは全て実行された直後にまとめる処理を実施します。まとめる処理というのは、非同期の処理をキューに格納していく作業になります。

非同期の処理そのものというよりは、非同期をするにあたって必要なキーというのをNext-TickのQに格納することということを指します。

### なぜ「同じイベントループ内」という制約があるのか

Next-Tickでなぜ区切るのかという質問に言い換えて回答すると、Next-Tickというのは非同期を処理するイベントループの中で最も優先的に処理される級になります。そのため、バッチ処理をNext-Tickのタイミングでやることによって、最も早くスピーディーに処理を実施することが可能になります。

これをNext-Dickじゃなくて、例えばプロミスであったり、setTimeOutといった比較的優先度の低い級に回してしまうと、処理するのが遅くなってしまいます。結果、他の処理が割り込んだりとかっていうのが発生して、データが混入したりとかっていう不具合につながる可能性があるため、なるべくバッチ処理っていうのはNext-Tickのタイミングで素早く処理する必要があります。

### バッチ関数のインターフェース

こちらの受け取る値keysですね。keysの入力の数と出力した結果の配列の数は一致していないとエラーになります。また注意点として、データローダーの中で返ってきた値の順番というのは、例えばDBから取ってきた場合は、keysの順番に並べ替える必要があります。

例えばABCというデータがあったときに、そのリザルトに対してABCというデータがあった際は、AはAに、BはBは2というひも付く関係が大事です。これが仮にCBAってなった場合はちゃんとABCの順に並び替える必要があります。

## Q2: DataLoader のキャッシュ機能

### キャッシュのライフサイクル

Cacheは基本デフォルトでリクエスト内だけで完結しており、リクエストが来てそれぞれロードが呼び出されます。その一発目のロードでCacheになかった場合、そのキーにひも付くプロミスをCacheします。次回以降の同じキーをパラメーターとするロードの結果は、キャッシュされたプロミスを返却するようになります。

全ての処理が終了した場合にキャッシュが破棄されるため、1回の処理の中でのキャッシュという意味になります。一連の処理が完了したらキャッシュは削除され、データローダーインスタンスも削除されます。

### なぜリクエストスコープにすべきか

リクエストをまたいでしまうと、本来であれば返すはずのない値をキャッシュを経由して返却してしまうというセキュリティ事故につながってしまう可能性があります。

例えば、Aというリクエストがあって、同時にBというリクエストもあったとします。いずれも返す値は同じですが、Bには返したくないというシチュエーションがあったときに、Aの値をキャッシュしたことによって、Bのリクエストでも同様の値を解決されてしまうケースがあります。そのため、こうした事故を防ぐために、リクエスト単位でAのリクエストだったらAのキャッシュを返すようにすることで、漏洩のリスクを抑えることができます。

### NestJS の Scope.REQUEST との関係

NestJSの場合は、キャッシュのスコープをScope.REQUESTと指定することで、キャッシュの有効範囲をリクエスト内に限定することができます。こうすることで、キャッシュがリクエストをまたいで活用されることを防ぐことができ、上記のセキュリティ事故を防ぐことにつながります。

補足すると、Scope.REQUESTっていうのは、NestJSが持つコンテナに注入するためのオプションみたいなもので、DataLoader固有のものではないですね。ほとんどのサービスっていうのはシングルトンになっていて、アプリケーションが起動した上で、それがずっと使い回されるっていう設定になるんですけど、\n\nDataLoaderといったものに関してはリクエストごとにコンテナを生成して破棄するということが必要になるので、その設定をDataLoaderに対して設定してあげる感じですね。

## Q3: DataLoader をGraphQL以外でも使えるか

### REST API や gRPC で使う意味はあるか

REST APIやgRPCで使う意味はあまりないかなと思います。後日に書いた通り、GraphQLで特にデータローダーが必要とされるのは、nプラス1問題を解消するためです。\n\nREST APIやgRPCは、結合処理などによりnプラス1問題を基本的には解消できるため、データローダーを使ううまみはあまりないと考えています。gRPCも同様です。要するに、あらかじめどういうリクエストが来るのかを想定しているものに関しては、N+1問題は起こらないので、そういう観点でいうと、REST APIやgRPCはあらかじめリクエストが決まっているため、エンドポイントに対するレスポンスをあらかじめ定義しておく形になります。

### なぜGraphQLで特にDataLoaderが必要とされるのか

GraphQLでは、レスポンスをフィールドごとに解決する性質上、N+1問題が発生しやすいです。これは、GraphQLがリクエストの形式を事前に把握できないため、レスポンスの準備を前もって行えないことに起因します。GraphQLではクライアントが欲しいデータを都度カスタムしてそれに答える形になるため、リクエストが実際に到達するまで何をしていいのかがわからないのです。

そのため、RESTでいう外部結合のようなことができず、例えばリストを返す際にそのリストの各項目に紐づくデータを連動して取得したい場合、項目一つごとにリゾルブする必要があります。これがN+1問題を引き起こすメカニズムになります。

GraphQLではこのようにN+1問題がクライアントの柔軟性とトレードオフで発生してしまうため、DataLoaderという仕組みを通じて処理回数を削減する必要があります。DataLoaderを使うことで、リスト内の一つのアイテムに対して一回一回リゾルブする必要がなくなり、MySQLでいうIN句のようなことが実現できます。結果的にクエリの発行は一回で済み、大元の発行を合計すると2回のクエリでN+1問題を解決できます。

### DataLoader以外のN+1問題解決アプローチ

一つの案としては、クエリを一本にまとめないやり方があるかなと思います。その分、クエリの実行元で仕組みを考える必要があるんですけども、例えば上記で言っているリストの中に一つ一つロードでリゾルバで解決しなきゃいけないような構造体を、そもそもリクエストしないという方法もあります。

例えば、booksっていうものがあったとして、そのbooksの中にauthorっていう著者のデータをセットで取ってくるようなことをするよりは、ブックは一旦単体で取ってきます。プラスオーサーをもう一本のクエリでまとめて取ってきて、それを呼び出し元でくっつけるようなマッピング処理をするっていう解決策もありますが、それはクライアントでやっちゃうとロジックが複雑化するし、責務の範囲を超えてしまうので、BFFで吸収するっていう考え方もあるかなと思います。

基本的にやらない方がいいと思いますが、そもそもリソースを分けないという考え方もあります。例えば、ブックスとオーサーというリソースがあった場合、それらをまとめて同じ領域として新たなリソースを生み出し、そこから参照するようにする方法もあります。
