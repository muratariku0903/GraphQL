# 演習2-1: class-validator によるInputバリデーション — 言語化回答

## Q1: GraphQLの型システムだけでは不十分な理由

### なぜ防げないのか

GraphQLの型システムだけでは構造の担保はできますが、一つ一つのフィールドの中身、値が適切かどうかまでは見ていません。間違ったデータが入ってきてしまう事態を招きかねません。例えば、Aというオブジェクトがあったとして、ネームとエイジがそれぞれストリングとナンバーでセットされる場合でも、エイジに-100といったありえない値が入ってしまうケースをスキーマだけでは防ぐことができません。値レベルでちゃんと適切かどうかを確認するために、バリデーションは別途必要になります。

### Resolver内で手動実装 vs class-validator + ValidationPipe

| | 手動実装 | class-validator + ValidationPipe |
|---|---------|-------------------------------|
| 関心の分離 |関心事がリゾルバー内で分散してしまうので良くないと思います。リゾルバーの役割はおそらくサービスへの振り分けだと考えています。このリクエストはこのサービス、このリクエストはこのサービスと、振り分けに関心を持たせるべきです。\n\nそこでバリデーションの定義を行うと、関心ごとが複数存在してしまう状態になると思います。 | Class-validatorとValidationPipeを使うことで、本来集中すべきリゾルバーの関心ごとを一つにまとめることができ、validationに関する関心は分離することができると思います。 |
| 再利用性 | ResolverにValidationを直接定義すると、似たようなValidationを他のモジュールから使いたいときに、そこからインポートする、あるいはまた同じような定義を再定義するといった事態が発生するので、再利用性は低いかなと思います。 |クラスバリデータとバリデーションパイプであれば、再利用性は高いかなと思います。フィールドごとにバリデーションのルールを適用していく形になるので、つまりフィールドごとに独立したルールをどこかで定義さえすれば、それを他のディソルバーで共有することができるという点で、再利用性は高いかなと思っています。 |

### 📝 レビュー（Q1）

正確な回答です。「構造の担保 vs 値の担保」の区分けが明確で、年齢 -100 の例も分かりやすいです。

**補足 — class-validatorの「宣言的」という利点:**

比較表で触れている内容に加えて、もう1つ重要な利点があります。class-validatorのデコレーターは **バリデーションルールをDTOクラスに「宣言」する** ため、そのクラスの定義を読むだけで「このフィールドにはどんな制約があるか」が一目瞭然です。

```ts
// 宣言的: クラス定義を読めばルールが分かる
@IsNotEmpty()
@MaxLength(100)
title!: string;

// 手動実装: Resolverの実装コードを追わないとルールが分からない
if (!input.title || input.title.length > 100) throw new BadRequestException();
```

特にチーム開発では「ルールの可視性」が重要で、「このフィールドに何が許可されているか」をDTOの定義だけで把握できるのは大きなメリットです。

Q1完了です。Q2に進みましょう。

## Q2: ValidationPipe がGraphQLでも機能する仕組み

### ValidationPipe の実行タイミング

実行のタイミングとしては、まずクライアントがリクエストして、そのリクエストをスキーマで構造チェックします。\n\nストリングなのか、ナンバーなのかという型のチェックが入り、その後にValidationPipeにてクラスバリデータの定義に従っているかをチェックします。最低限の構造チェックを突破した後の具体的な各フィールドのチェックをします。このタイミングでValidationPipeが実行されます。

### REST の @Body() と GraphQL の @Args() での違い

RESTのボディはリクエストで渡ってきたボディ全体ですね。ID、ネーム、エイジみたいなのがあったら、その3つ全部がボディで受け取られ、それぞれに対してすべてValidationPipeによって値チェックが行われます。

GraphQLの場合は、Argsの引数で指定した項目のみバリデーションチェックの対象になります。例えば、id, name, ageとなっていて、そのリクエストのうちネームというのを指定したら、そのネームがクラスバリデータで検証されることになります。

### class-validator デコレーターの評価の流れ

まず、リクエストを受け取ったら、GraphQL がプレーンオブジェクトというのを ValidationPipe に渡します。前提として ValidationPipe の transform 設定が有効化されている前提で説明すると、プレーンオブジェクト、いわゆる JSON だと思うんですけど、それを受け取った ValidationPipe は内部でインスタンスにトランスフォームする処理を実施します。

いわゆる TypeScript のクラスに変換する処理です。こうすることによってメタデータが設定された構造体に変換できるため、このメタデータを参照して class-validator が機能します。この class-validator っていうのが、そのクラスの各フィールドに定義されたルールに従ってバリデーションチェックを実施し、問題があればそれをまとめて返すという流れになります。なので大事なのは、JSON をちゃんとした TypeScript のクラスに変換し、そのメタデータが設定された状態のもとで、class-validator のデコレーターが認識されるという形です。

### 📝 レビュー（Q2）

全体的に正確です。特に `transform: true` の役割（プレーンオブジェクト → クラスインスタンス変換 → メタデータが認識される）の説明は本質を捉えています。

**1点修正:**

`@Args()` の説明で少し認識がずれている点があります。`@Args('input')` は「リクエストの引数のうち `input` という名前のものだけを取り出す」という意味であり、「特定フィールドだけバリデーション対象にする」という意味ではありません。

実際の流れは：
1. クライアントが `createBook(input: { title: "...", authorId: "...", genre: FICTION })` を送る
2. `@Args('input')` が `input` 引数全体（`CreateBookInput` オブジェクト）を取り出す
3. ValidationPipe が `CreateBookInput` クラスの**全フィールド**に対してバリデーションを実行

つまり REST の `@Body()` がHTTPボディ全体を対象にするのと同様、`@Args('input')` も引数として渡されたオブジェクト全体が対象です。大きな違いはありません。

NestJSの設計上、**ValidationPipeはトランスポート（REST/GraphQL/gRPC）に依存しない**ように作られているので、REST でも GraphQL でもPipeの挙動は同じです。これがNestJSの「プラットフォーム非依存」の設計思想の恩恵ですね。

Q2完了です。Q3に進みましょう。

## Q3: バリデーションエラーのレスポンス設計

### GraphQL でのバリデーションエラーの形

 RESTと異なり、バリデーションエラーになったとしても、まず200で返ってきます。HTTPステータスは200です。その中にerrorsという配列が存在し、その各要素の中にエラーメッセージなどが格納されている形となっています。

### フロントエンド（urql）でのエラー受け取り方

URQLなどのライブラリを使えば、内部でGQL名に成功と同様の200で返ってきたとしても、エラーだった場合はパースしてエラーオブジェクトを受け取れるようになっています。エラーズという配列をフロントで持ち回って、GQL名にメッセージを抽出して表示するというような使い方になるかと思います。

### REST のエラー（HTTP 400）との比較

RESTと違って、ValidationErrorでも200を返すことになっていて、これがなんで200で返すのかというと、GraphQLでは部分的な成功というのを認めているからですね。

エラーになった場合は、レスポンスにそもそもデータとエラー図という2つの項目があって、成功した場合はデータに入り、失敗した場合はエラー図に入るということになるんですが、GraphQLの場合は部分的な成功を認めていて、データとエラー図というのは共存する状態が存在します。

部分的に成功した場合、一部の項目は成功したけど一部の項目は失敗しましたよ、みたいな挙動が実現できるということになるので、バリデーションに失敗したからといって400では返すのではなく、200っていう部分的に成功したよっていう意味合いで200を返すという風になっています。

### 📝 レビュー（Q3）

3観点とも正確です。特に「部分的な成功（partial success）」という概念に触れてGraphQLが200を返す理由を説明できているのは良いポイントです。

**1点補足 — ValidationPipe のエラーは実は「部分成功」にならない:**

「部分的な成功」の説明は GraphQL のエラーモデルとしては正確ですが、**ValidationPipe のバリデーションエラーの場合は、実は部分成功ではなくリクエスト全体が失敗します**。

理由は、ValidationPipe は**Resolverが実行される前**の Pipe 段階でエラーを投げるため、Resolver自体が一度も実行されません。つまり `data: null, errors: [...]` という形で返ります（`data` に部分的な値が入ることはない）。

部分成功が起きるのは、**Resolverの実行中**にエラーが発生した場合です。例えば：
```graphql
query {
  book(id: "1") { title }      # → 成功
  book(id: "999") { title }    # → Resolver内でエラー
}
```
この場合、1つ目のbookは `data` に入り、2つ目のエラーは `errors` に入る — これが真の部分成功です。

→ つまり「なぜHTTP 200を返すか」の正確な理由は、「GraphQLの仕様でエラー応答もHTTP 200と定められている」というのが本質で、部分成功はその理由の1つという位置づけです。
