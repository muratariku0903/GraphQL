# 演習2-3: ページネーションとフィルタリング — 言語化回答

## Q1: Offset-based vs Cursor-based ページネーション

### Offset-basedの仕組みとメリット・デメリット

まずメリットとしては、オフセットリミットっていうのをそのままクエリに渡す形になるので、実装がすごくシンプルになります。オフセットとリミットを渡せばいいだけなので。さらに、オフセットでページ番号を指定してあげることで、特定のページにジャンプすることができると思います。なので、例えばページネーションで番号付きのページネーションボタンが存在して、例えば1ページだったところから5ページ目までにジャンプするみたいなことができます。

以上がメリットで、デメリットとしてはオフセットが大きくなると、その分パフォーマンスが低下するっていう問題があります。オフセットが例えば10とか20とか小さい数であれば問題ないですが、例えば1万とかだとすると、DB的にはまず1万行スキップしてそこから何件取るみたいな処理が発生するので、パフォーマンスに負荷が大きくかかってしまうっていうのと、あとは途中のDBのデータの増減に影響を受けてしまうっていうのがあります。

極端な話、例えば1ページ目を開いてて10件データがありましたってなったときに、じゃあ2ページ目に行くと仮定して、その間に最初の1ページ目に見ていたデータの前に10件のレコードが生成された場合、どうなるのか。そうすると、単純に2ページ目に遷移したときに1ページ目の内容が同じく表示されるといったことが起こるんですよ。

オフセットっていうのは、例えばオフセット10を指示したら10ページ目までスキップしてそこから取るっていう意味になるので、逆に言うとその間にオフセットより前にデータが追加されてた場合、すでに取得してあった情報を取ってきちゃうことになるんですよ。ということで、重複したデータ取得っていうのが問題になるケースがある。

### Cursor-basedの仕組みと利点

カーソルは基本的にどこから取ってくるかっていう判断をする際に、オフセットみたいなものではなくて、次のデータを取得するっていう風な判断をしています。特定のアイテムの次から取得するっていうような扱いになります。なので言ってしまえば、データを取得した時点でその次のデータの開始点っていうのは決まってるわけなんですね。

データのない構造が変わったとしても、次回以降取ってくるデータっていうのはNextカーソルで確定してる状態なんですよ。例えば10件取得しますで、次の取得に関しては10件の末尾のノードから次になるという風になるので、データの追加とか削除といった影響をまず受けないというのが利点としてあります。

ただデメリットとして、オフセットみたいにページジャンプができないです。あくまで取得した末尾のノードの前後からっていうようななる、末尾かどうかっていうのもちょっと指定はできるんですけども、要は特定のノードの前とか後ろとかっていう指定方法になるので、ページ番号を指定してそこからジャンプするっていうのはできないです。

### Cursorとは何か

カーソルは一言で言うと、どこからデータを取ってくれるかの起点かなというふうに思ってます。基本的にカーソルは、特定のノードから前後のデータを何件取ってくるかっていう扱いになるんですけど、そこの特定のデータを指し示す場所がカーソルになります。基本的にIDだったりタイムスタンプだったりするんですけど、ベース64でエンコードされている形になってます。

なんでこれがエンコードされているのかというと、基本的にクライアントからカスタムされるっていうのを防ぐためというよりも、どういうデータなのかっていうのを隠蔽するためですね。隠蔽することによって、クライアントはそれをよしなり編集したりだとかっていうのがしにくい状況を作ることができるので、そのままカーソルを編集せずにそのままリクエストに付与するみたいな流れを作ることができると思っています。

仮にこれが例えばIDだったりとかっていう普通のPKとか、という意味を推測できるようなものを渡してしまうと、例えばクライアントでPKにプラス10してリクエストに増やしちゃったら、そこから起点取れるんじゃないかみたいな、開発者、バックエンドの意図しない使われ方っていうのをしてしまう余地があると。という意味で、とりあえずカーソルは何も触らないでねっていうような抽象化の壁を作る上で、カーソルっていうのは変コードしておくっていうのがカーソルベースの哲学になります。

## Q2: Relay Connection仕様

### 各フィールドの役割

### なぜEdgeでラップするのか

dgeっていうのは、それぞれのデータですね。返ってきたデータです。例えばユーザー実験だったら、ユーザー実験が配列で入ってきます。ユーザーのデータだけじゃなくて、カーソルもセットで入っている感じですね。なので、Edgeっていうのはカーソルとデータ、この2つを組み合わせたものです。それが配列でEdgesに入ってきます

また、エッジとデータで分離することによって、関心の分離ができるかなと思います。例えば、これを分離せずに「データ」という一つの中に取得してきた固有の情報とカーソルを混ぜちゃうと、表示したいデータとページネーションで使いたいデータっていうのがごちゃごちゃになってしまいます。

なので、あえてカーソルというのとデータという2つの概念に分けています。このように役割ごとに分けることで、関心の分離ができます。

### PageInfoの各フィールドの使われ方

PageInfoっていうのは、次回以降のページネーションをするときの必要な情報です。例えば次のページがあるかとか、多分UIでページネーションのボタンとかを表示するために必要なデータが入ってくるかと思います。

### totalCountについて

トータルカウントっていうのは、総件数になります。データ取得してきた総件数、つまり10件取ってきたら10という値が入るかと思います。

上記が誤解がありまして、フィルターにヒットする総件数になります。なので10件取ってきたら10件じゃなくて、10件だったらそれは別に取得する必要はありません。

## Q3: フィルタリングの設計

### フィルタ条件のInputType設計

まず大きく分けると、2つの構造、2つの項目を持つオブジェクトとなっていて、まずはカーソル情報ですね。2つじゃなくてもいいので、ファーストとアフターを持たせて、カーソルの起点とそこから前に何件取ってくるのか、あるいは後ろに何件取ってくるのかみたいなデータ取得の方式についての情報を含めます。

あとは別途フィルタリングっていうオブジェクトを用意して、そこにそれぞれの検索項目をどんどん入れていくやり方でいいと思ってます。例えばフィルタリングだったら、名前とかエイジっていうのがそのオブジェクトの中に入るイメージです。今回の場合は、ジャンルと出版年というのをフィルターのオブジェクトの中に入れていくイメージです。ヌル許容にするのか、それともアンデファインドにするのかは、実装の設計次第だと思うんですけど。

### totalCountは何に対するカウントか

トータルカウントはフィルターでヒットしたデータの総件数になります。

### フィルタ条件が増えた場合のスケーラビリティ

フィルターの条件が増えた場合は、普通にフィルターというオブジェクトの中にどんどん格納されていくだけなので、大まかな構造は崩れないというメリットがあるかと思います。なので、方式としてはフラットに並べるんじゃなくて、フィルターはフィルターでネストしておくっていうところが大事かなと思います。
