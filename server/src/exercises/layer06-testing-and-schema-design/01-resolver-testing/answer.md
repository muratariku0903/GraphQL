# 演習6-1: Resolverテスト — 言語化回答

## Q1: Resolverテストで何をモックし、何を実際に実行すべきか

### モックすべきもの と 実際に実行すべきもの

モックすべきものはリゾルバーで呼び出されているサービス、データベースと直接やり取りする層になります。また、コンテキストなどを使用している場合、そういったものも別途モックが必要になります。

実際に実行すべきものとしては、リゾルバーのフィールド解決のロジックになります。例えば、サービスに渡している引数が適切なものかどうか、Parentを使って親オブジェクトを参照している場合は、そちらも適切な流れになっているかをチェックし、実際のロジックでテストすべきです。

なぜそもそもサービスはMockするのかについてですが、ここで単体テストにおいてチェックしたいことっていうのはリゾルバーの挙動になります。受け取ったリクエストを正しくDTOしてサービスにつなげるっていうそこの挙動であったり、逆にそのサービスからのレスポンスを正しく整形したりエラーハンドリングしたりということにのみ関心を持つので、逆に言うとそれ以外のロジックについてはMockで関心から切り出すということが必要になるからです。

コンテキストのMockについてですが、こちらはリクエストオブジェクト、ローダーファクトリー、リクエストIDなどがMock対象になります。

### @ResolveField のテスト

単体テストの場合は、ペアレントデコレーターで受け取る値をそのままMockとして用意する必要があります。
統合テストの場合は、親オブジェクトからの参照も含めて、Mockなどはせずにそのままテストします。

ResolveFieldを扱うとN+1問題が発生する可能性があると思います。ただ、単体テストでは実際にN+1問題が起こっているかどうか、あるいはそれを対応できているかどうかをテストのスコープに含めることはできません。例えば、ポストが10件あるとオーサーが10回呼ばれるような状況をチェックしません。

あくまで、Mockを使って1件だけポストを用意し、そのポストのオーサーIDでオーサーが呼ばれているか、つまり親オブジェクトから子オブジェクトが正しく参照できるかをテストするだけになります。そのため、N+1の挙動についてはスコープの対象外ということになります。

ResolveFieldのテストにおいて、クエリを受け取ってそれをDTOに変換し、サービスにつなげるまでが単体テストの責務になります。実際にそれよりもっと広くリクエストを受け取って、このクエリだったらこのResolveFieldが呼ばれるはず、みたいな全体を通したテストにおいては統合テストでやる形になります。

実際にResolveFieldを必要とするフィールドをクエリに設定するときとしないときで動作をチェックするようなテストに関しては、統合テストでやる形になると思います。

### DataLoaderが絡む場合のテスト

DataLoaderは単体テストではMockをして、統合テストでは実際にMockをせずに、実際のDataLoaderの動きを通してテストします。

DataLoaderの本質っていうのは、Nプラス1問題の解消を対応するためのバッチ化になると思います。こちらのバッチ化がちゃんとできているかどうかっていうのは、単体テストだけだと不十分で、統合テストの中で検証していくものになります。

例えば、10件のポストがあったときにバッチ化を実施していない場合は、オーサーっていうクエリが10回呼ばれるわけなんですが、バッチ化をちゃんとしている場合は、1回だけのオーサーで取得できているっていうところの検証になるかと思います。実際にDataLoaderの中でデータベースとやり取りしている部分に関しては、そこはMockできるかなと思っていて、要するにクエリの実行が何回発生しているのかっていうところをチェックできれば良いということになると思います。

バッチ関数自体をスパイにしてあげることで、より効率的にテストを回すことができるかなと思います。

## Q2: ユニットテスト vs 統合テスト の使い分け

### それぞれのテスト対象の範囲

ユニットテストでは、Q1に説明した通り、リクエストとサービスの橋渡し、また逆にサービスからアウトプットへの橋渡しの中間ロジックのテストになります。例えば、リクエストに渡された何かしらのパラメータがサービス層に適切な形にして渡されているのか、そしてサービス層から返ってきたレスポンスというものが適切なフォーマットに変換されて最終的にエンドポイントの結果として返却されるのかっていうところのテストっていうのがスコープになります。

対して統合テストの場合は、そういった一連の流れを超えて実際のクエリを流して、実際のコードでリゾルバー、実際のコードっていうのはリゾルバーの部分ですね。サービスは多分 Mock するとは思うんですけど、もっと広く広いテーマにテストをする感じになります。例えば、Resolver の周辺ではパイプ使ったり、ガードといった認可のレイヤー、あるいは入力者検証のレイヤーなどがあると思うんですけども、そういったところがちゃんと適切に動いているかっていうところも踏まえてテストします。また、実際のクエリを流すので、DataLoader のテストもできるかなと思います。N+1 問題がちゃんとバッチで解消できているかっていうところですね。

ユニットテストとの違いとしては、ユニットテストはあらかじめ事前に「こういうリクエスト」というのをテスト用に用意するんですけども、統合テストに関しては実際のクエリっていうのを流してみて、ユニットテストのマイクロの部分だけじゃなくて、しっかりリゾルバー層全体のテストをできるっていうところが違いかなと思います。



### 比率と判断基準

ユニットテストと統合テストの比率としては、7対2っていうのがテストピラミッドの方向によって一般化されているものとしてあると思います。なぜユニットテストが多くて統合テストが少ないのかについてなんですが、まずユニットテストというのは単純にテストがしやすく、かつ網羅的にテストができるというところが大きいと思います。テストを回すための時間も高速ですし、単体テストなので、よしなに自由にデータを用意して実行ができると、そういったときに様々なエッジケースの検証などができる。

また、テストの工数というのも統合テストと比較して簡単に実装ができるものになるので、比較的統合テストよりはかなり量が多くなるかなと思います。逆に統合テストの場合は、テストを実行するのにおいて単体テストよりも時間がかかりますし、そもそもテストを書く、テストの環境を用意するというところ自体に時間がかかってしまうものになるので、量としては単体テストよりは少なめになる。

ただ、なので統合テストとしては全部カバーするっていうよりは、クリティカルな部分だけをちゃんと最低限チェックしようみたいな方向に倒す感じになると思います。

GraphQLはRESTと比較して、ガードパイプライン、エグゼプション、データローなど、様々なレイヤーが複数存在するため、統合テストの厚みが重要になってきます。そのため、単体テストは別途行いますが、統合テストで全体をつなげたテストを重点的に行う考え方もあります。

### 統合テストでしか検出できないバグの例

単体テストだとResolverのロジックのみのテストになるので、逆に言うとそれ以外の不具合みたいなのは統合テストで補足する感じになるかなと思います。

例えば、データフロー、ガード、バリデーションパイプといったエコシステムの部分がちゃんと動作しているかといったところは、統合テストでしか検出できないものかなと思います。要するに、外側でリクエストを制御するインフラみたいな部分は、多分単体テストでは無理で、統合テストでしか検出できないものかなと思ってます。

では、具体的な例を出すと、まずガードについてですが、例えばこのリクエストだったら本来ガードレイヤーで拒否されるはずなのに、実際にテストを通してみたら通ってしまった、みたいなケースがガードの具体例になります。\n\nValidation pipeについては、入力値の検証なので、例えば文字列のデータだったのに数値を設定したクエリを実行してもそれが通っちゃった、というような漏れですね。データローダーのバッジについては、例えば10件のポストがあったとして、そこでオーサーを10回実行するっていう場合に、バッジを設定した状態で実行したときにオーサーが、本来だったら1回しか呼ばれないはずなのに10回呼ばれてしまっている、といったそういったところが発見できるバグなのかなと思います。

また上級機器以外の例としては、エラーフォーマットが適切に機能しているか、例外投げたときにエクステンションズの中に意図通りのエラーコードが付与されているかということですね。これが付与されていないんだったら、エラーフォーマットが適切に動作していないということになると思います。

またフィールドを付け忘れたフィールドをクエリに投げるとエラーになるみたいなところは単体テスト上では取ってしまうかなと思います。これは要はGraphQLとNest.jsのインテグレーションの部分の設定になるので、これは単体テストだけでは見逃してしまうかなと思います。

## Q3: GraphQLテストの落とし穴

### スキーマの自動生成とテスト

統合テストをする際は、クエリを実際に流し込んでテストするため、前提としてスキーマが生成されている必要があります。Code First の際は、トップレベルのモジュール設定でオートスキーマファイルトゥルーの設定をしておくことで、起動時に自動的に GraphQL のスキーマが生成されるので、スムーズにテストができると思います。\n\nそのため、統合テストをする際は、トップレベルのモジュールにてテスト自動設定とスキーマ自動生成の設定を追加しておく必要があります。

スキーマの変更を単体テスト側は即座に検知することができないので、例えばデコレーターのフィールドの値というか設定を変更したとしても、そのまま単体テストはパスしてしまうという落とし穴があります。タイプスクリプトで単体セットが実行されているという前提なので、タイプスクリプトは単体セットでスキーマ関係なく実行できてしまうというところがこの問題の本質的な問題かなと思います。

なので解決策としては、スキーマが変わってたらテストを落とすっていうようなテストの項目を1個用意してあげるっていうのがあるかなと思います。この単体テストでは、スキーマの変更がされてませんよっていうところを担保するためのテストケースですね。

### HTTP 200固定のテスト成否判定

 GraphQLの場合は基本的にhttpステータスっていうのは失敗だろうが成功だろうが200を返しますこれレストと違ってレストの場合は200だったり選択をきてたら500だったり404,403,400みたいなのが書いてくるんですけどGraphQLの場合は全部200で書いてくるので200が来たから成功しましたみたいなというふうに判断、安易に判断するべきものではない。つまりステータスコードを見て結果を判断するべきではないということですね。ステータスコード以外のErrors Objectっていうのがあるので、Errors Objectだったりデータとかを見て、ちゃんと期待通りに動いているかどうかっていう判断を下す必要があります。例えば正常系のテストをするんだったらまず200で返ってきていることに加えてデータがちゃんと期待値になっているかエラーズが存在しないあるいは空配列になっているか逆に異常系であればデータが 存在するかどうかっていうのはグラフQLの場合オプショナルの概念もあるのでそこはそんなに大事じゃなくてまずエラー図があるかですねエラー図にちゃんとあるのかエクステンションズコードっていうのが想定内のコードなのかっていうところをチェックすることになると思いますあくまでステータスコードだけじゃちゃんとテストできてるか判断はできない

### Mutationの副作用確認

ミューテーションの副作用確認に関して、ミューテーションは結果だけ、レポンスだけを見るだけじゃ不十分で、実際にそれによってデータベースの内容がどういうふうに変わっているのかっていうところまで確認する必要があります。なのでミューテーションを実行してその結果が正しいことに加えて、再度それによる副作用が確認できるようなクエリを実行し、その結果が正しい予期した値かどうかまでチェックするっていうのが基本的な流れになります。

インメモリデータの場合と実際のDB接続の場合でやり方がちょっと変わってきていて、インメモリデータの場合であれば、ミューテーションした後のクエリ実行だけで基本的には良いかなと思います。DB接続の場合は、実際に使っているDBを汚さないようにするために、基本的にはテスト用のDBをまず作成し、そこでミューテーションの副作用のチェックをすることになると思います。

また、テストしたらDBの状態を元に戻した方が良いと思うので、テスト全体をトランザクションでくくって、最後にロールバックするっていう仕組みが、一応テスト環境をクリーンに保つ上で必要かなと思います。あとは副作用の確認としては、インメモリデータの場合と同じようにクエリ発行をしていく形で良いかと思っています。
