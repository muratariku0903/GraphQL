# 演習6-2: スキーマ設計とバージョニング — 言語化回答

## Q1: GraphQLのバージョニング戦略

### URLバージョニングを採用しない理由

GraphQL の設計思想に関連して、GraphQL は複数のエンドポイントを持たず、一つのエンドポイントを段階的に進化させていくという設計思想を持っています。後続の説明にもある通り、Deprecated というディレクティブを使って、そのエンドポイントで取得できるフィールドを徐々に更新していくやり方を採用しています。\n\nそのため、URL バージョニングをして複数のエンドポイントを設けるということはしません。

仕組み的な面で言うと、GraphQLというのはクライアント側が参照するフィールドを適宜選べます。なのでそのフィールドさえ維持しておけば、たとえ既存のエンドポイントに対して新しいフィールドを追加しようが、クライアントが壊れることはありません。

つまり、エンドポイントに対するフィールドの追加っていうのをしたとしても、互換性、交互互換性は保たれるっていう本質的な仕組みっていうのが存在します。なのでエンドポイントを分ける必要はありません。一つのエンドポイントで、そこに対してフィールドを追加したりするっていう対応で大丈夫です。

### @deprecated の役割

そのエンドポイントを呼び出すクライアント側に、そのフィールドが非推奨であるということを報告するためのディレクティブになります。例えば「フルネーム」というフィールドが存在して、それが新しく「ネーム」というフィールドになるとなったときに、「フルネーム」の方に「@deprecated」というディレクティブを付与してあげます。そうするとクライアント側に「このフィールド名は非推奨です」ということを伝えることができます。

また、「reason」というプロパティに理由を設定できるので、どういう理由でこれが非推奨だったのかっていうのがクライアント側は把握できるようになります。さらに、Apple Serverとか、いわゆるスキーマを実行できるサービスでも、「@deprecated」というのが付いているフィールドは他のフィールドと区別できるような仕組みになっています。クエリを呼び出すときに、推奨フィールドなのか非推奨フィールドなのかっていうのが一目で分かるようになります。

RESTとの違いとしては、RESTの場合はエンドポイントレベルで分離しますが、GraphQLの場合は一つのエンドポイントの中で古いフィールドと新しいフィールドが混在する状況となるので、その進級を区別するために@deprecatedっていうディレクティブが存在します。

### フィールドの廃止プロセス

前日で知った通り、段階的にフィールドを廃止していきます。まず、最初に非推奨フィールドとなったものに対して @Deprecated のディレクティブを付与します。そうすると、クライアント側がこのフィールドは非推奨なんだなっていう把握ができるので、徐々に @Deprecated フィールドっていうのを全部が削除され終わったら、@Deprecated のフィールドが付いているものを削除します。

具体的に「name」というフィールドについてプロセスを提示すると、「name」がフルネームになるというプロセスになります。まず、「フルネーム」という新しいフィールドを追加します。この段階では互換性は維持され、クライアントは壊れません。

次に、古いフィールドである「name」に対して `@Deprecated` ディレクティブを付与します。クライアントはこれを受けて非推奨の「name」を全て削除します。全ての削除が完了次第、スキーマから非推奨となっているフィールドを削除します。こうすることによって、クライアントが壊れずに段階的にスキーマを進化させることができます。

必須となるフィールドがアプリケーションから使われなくなったかどうかを判断する手段として、まずそのエンドポイントが内部のアプリケーションで完結するのか、それとも外部からも呼び出されているのかという2つのケースによって、判断方法が異なると思っています。

まず内部の場合であれば、例えばリポジトリの中でその Q フィールドをグレップなどで検索し、一つもヒットしなかった場合など、コードジェネレーターを使用している場合は、ジェネレート時に deprecated が存在する場合に警告が出るため、その警告がなくなったタイミングが一つの判断材料となります。

外部公開の場合は、不特定多数のクライアントが存在するため、実際のリクエストログを収集し、そのログで deprecated のフィールドが呼び出されているかどうか、呼び出されていないカウントが一つも存在しないなどの記事を設けて、そこに従って実際に削除するかの判断をすることになります。

## Q2: 良いスキーマ設計の原則

### スキーマ設計の原則（3つ以上）

一つ目の原則として、まず命名規則というのがあります。スキーマでは様々な概念が存在するんですけども、例えば型名であったりフィールド名であったりリーナムの値であったりミューテーションだったり、そういったものに対して命名規則というのを設けて、それを守るということをすると可読性が上がるかなと思います。例えば、型名だったらパスカルケース、フィールド名だったらキャメルケース、リーナムだったらスネーク、ミューテーションは動詞プラス目的語にするといった命名規則を設けることによって、これは型だな、これはミューテーションだなという判断がすぐにできると思います。

逆にアンチパターンとして、全ての概念に対してスネークケースを適用してしまうと、パッと見たときにそれが何をどこで使われるのかとか、どういう役割なのかっていうのがすぐに判断できない状態になってしまいます。なので、パッと見で分かるために命名規則を大事にすることがまず1点あります。

型の流度としては、型の流度っていうのは2点目としてあると思っていて、適切な流度で型を設けるっていうのがあると思います。アンチパターンとしては、ちょっと細かすぎる流度でクエリを定義しているとか、例えばユーザーっていう概念があったときに、そのユーザーのネーム、ファーストネームとかラストネームとか、っていうそのユーザーの一つ一つの属性で型を作っちゃうとか、あるいはその一つ一つの属性に対応したクエリを用意する。こういうことをしてしまうと、GraphQLの旨味っていうのが全然活かされないことになってしまいます。クライアントからはその属性に対応したクエリを毎回毎回呼び出しなければいけなくなっちゃう。なので実装も複雑化してしまうので、ネットワークの通信とかも大きくなっちゃいますし。

そうではなくて、ちゃんとさっきの例だとユーザーっていうような型を設けて、ユーザーを返す一つのクエリを用意します。そのユーザーの中にネームだったりファーストネームだったりラストネームだったりっていうのを管理するようにすることによって、一つのクエリでクライアントが適宜取得するフィールドを選ぶ形にしてあげれば良いかなと思います。っていうのが型の流度による原則の一つかなと思います。

3つ目の原則としては、インプット型の分離ということで、ミューテーションを定義するときに例えばクリエイトユーザーみたいなミューテーションを用意したときに、引数に多分結構ユーザーのフィールド分用意したくなっちゃうとは思うんですけども、そうではなくて、クリエイトユーザーインプットっていう一つのインプット型っていうのを用意してあげて、そこにどんどんファーストネームだったりラストネームだったりユーザーを構成するフィールドを設けるっていうような形にしてあげると良いかと思います。なんでそういうことをするのかっていうと、まずパッと見で複数の引数を設けるよりも、クリエイトユーザーインプットっていう一つの型を設けた方がまず分かりやすいっていうところと、あとはそのCreate User Inputっていうのをクライアント側で使い回すことができるようになります。なので、バリデーションロジックの共通化などにも利用できるので、複数の引数を与えるよりも汎用的にクライアントの処理が適用できるっていうところのメリットがあると思います。

3つ目のインプット型の分離っていうのは、ちょっと下で述べてる内容と重複しちゃうんで、4つ目の原則を追加します。4つ目の原則としては、日付データを文字列で定義するのではなくて、カスタムスカラーを使って「デートタイム」っていうのを定義して、デートタイムを使うっていうことですね。

文字列っていうのが何でアンチパターンなのかっていうと、日付の表現方法っていっぱいあるじゃないですか。タイムスタンプだったり、年月日付っていうのも配布でつなげたりだとかっていうフォーマットが定まってない、複数存在するといったときに、クライアントっていうのはそこに引っ張られちゃうと。例えば、そのフォーマットをちょっと変えたときにコンパイラーが発生したりだとかっていう、かなりリスクが大きいものになっちゃうんで、「デイトタイム」っていうのは必ずこれっていうのを一発で定めて、クライアントはそれを信頼して吉野にフォーマットを変換するっていうのが正しいやり方かなというふうに思います。

また、「デートタイム」っていうスカラーを用意しちゃえば、バリデーションとかも適用できることになるんで、文字列だと文字列って全部バリデーション通っちゃうんで、そういうフォーマットの違いみたいなのを検出できないんで、「デートの型」っていうのを一個用意してあげてっていうことをすれば、クライアントが壊れることもないし、バリデーション適用できるし、っていう面でより安全なリストになるかなと思いました。

### Nullable設計の判断基準

nullable の設計判断基準としては、その方がビジネスロジック上で null に何言えるケースが存在するのか否かっていうところが大事かなと思ってます。例えば、ポストっていう方が存在したときに、そのポストにタイトルがないなんてことは絶対ありえないわけじゃないですか。そうするとポストって何ってなっちゃうんで、そういうこの概念に対しては「このフィールド確実に存在するよね」というようなビジネス上のルールに適用して、フィールドごとに「これはヌルを許容する」「これはヌルを許容しない」というのを判断していくことになるので、それはビジネスロジックの都合次第が答えかなと思っています。

他の観点としては、ヌルのバブリングが発生するので、その項目が取得できなかった場合は、ヌルを許容していないノンヌルなフィールドなのにも関わらずヌルが入ってきちゃった場合、親のフィールド自体が全部ヌルになっちゃうっていう現象が発生するので、そういった現象をあらかじめ抑制したいっていうのであれば、そのフィールドはノンヌルではなくてヌルエラブルにしてあげるっていうのも一つのやり方としてあるかなと思います。

なので、ノンヌルなのにそれがヌルエラブルが入ってきちゃう可能性があるんだとしたら、ヌルエラブルにしてあげる必要があると思います。まあ当たり前なこと言っちゃってるですけど。

上記は個々のフィールドに対してヌル許容にするのか、ノンヌルにするのかっていう判断の話になります。開発チーム全体として基本ヌルエイラブルにする方がいいのか、ノンヌルにする方がいいのかっていう話になると、基本的にはノンヌルにするっていうのが大事です。特定の理由があった場合のみ、ヌル選択にする基本はノンヌルにするっていう方針が適切だと考えています。

そうすることによって、クライアントがこのフィールドはヌルかどうかっていうのを意識することがなくなるため、実装がかなりシンプルになります。また、もしヌルが送られてきたときに早期にバグを発見することができるっていうところが大きいメリットの一つかなと思います。

### Input型を分ける理由

まず、インプット型を分ける理由として、引数ではなくて一つのインプットという型を用意してそれを使うことによって、コードジェネレーターなどで型生成したときにその型をバリデーションロジックに組み込めます。そこがすごく便利かなと思っています。また、Q-1でも出てきた後方互換性を保ちやすいという点も大きいかなと思っています。

インプット型を用意せずに引数で受け取っていた場合、バージョニングを上げるときに例えばこの引数を増やしたりすると、多分クライアントにも影響が出てきますよね。なので、一回インプットというインターフェースを設けて、そこでフィールドを追加したりするようにしてあげれば、クライアントを壊しにくい設計になるかなと思っています。

インプット型の設計でクリエイト用とアップデートを分ける理由を型安全性の観点で説明するについてなんですけど、そもそもクリエイトとアップデートって全く別の処理ですよね。クリエイトは新たに生み出すものなので、全てのフィールドが存在しなきゃダメですよね。アップデートっていうのは更新になるので、一つでもフィールドが存在すればそれは成り立ちます。それに、どこをアップデートするのかというIDが必要なので、根本的にインターフェースと役割が全然違うものになります。

なので、それらを分離することはとても当たり前のことです。フィールドの個々のフィールドが渡すフィールドが共通的に扱えるという点はそうなんですけど、意味合いが全然違うので、意味合いが違うものを同じインプットという方にしちゃうと、どこかで絶対バグが発生します。そのため、分けるっていう判断は適切かなと思います。

クライアント側も迷わないんで、新規なんだって言ったらクリエイトの方を使えばいいし、これ更新なんだって言ったらアップデートの方を使えばいいじゃないですか。そういう迷いもなくなるっていうのもメリットの一つかなと思います。

また、型安全性の面としても、それぞれ2つに分けてあげることで、コンパイル時にもしそれが不適切な型であったらエラーで検出することが可能になります。これが1つの型によってまとめられていたら、コンパイル時にエラーを検出できないですよね。なぜかというと、多分クリエイトとアップデートを一つの型にするってなると、全部多分オプショナルにすると思うんですよ。

IDとかもそうです。なので、クリエイトとして使ってるのに、例えばタイトルがないみたいなやつも本来であればコンパイルエラーのはずなのに、エラーで通してしまうっていうところがあります。そのため、それぞれの用途ごとに対してバリデーションの検出ができないっていうのが、型安全性を壊してしまうことになります。

なので、インプットとアップデートでそれぞれ型を分けてあげて、ドキュメントとしてもそうですし、コンパイル時のエラーを厳密に適用させるっていうチェッカーとしての意味、この2つの意味で型安全性を担保できるかなと思います。

## Q3: GraphQL Code Generator

### 解決する問題

まず2点ほど解決する問題があると思います。1点目は、まず単純にスピードが速いという点です。自動で生成してくれるので、手動で型定義する場合に比べてミスが起こりません。ヒューマンエラーがないだけでなく、手動の時よりも圧倒的に速く型を生成できます。

あとは型の安全性ですね。これはスキーマと型が常に同期している状態を実現できるため、実装されるコードが必ずスキーマに準拠している状態を担保できます。型安全性が高くなります。

例えば、何かしらのスキーマが存在して、それに合わせたミューテーションやクエリのTypeScriptコードがあったとします。スキーマが変更された場合、自動的にそれを検知して実装部分に反映されます。そうすると、型の変更が即座に検知され、エラーとして通知されます。例えば、ミューテーションの引数に1つ追加した場合、TypeScriptの型もそれに反映されるので、引数が足りないといった問題を即座に検知できます。

これはランタイムエラーになる前に事前に教えてくれるため、開発者にとって非常に大きな恩恵があります。手動でやる場合、反映漏れなどの問題があるため、動機が取りにくくなります。コードジェネレーターを使うと、必ずスキーマとコードが同じ型を持つことが担保されるため、型安全性が高いです。

### サーバー側 vs クライアント側での必要性

前提として、サーバー側でスキーマファーストで実施している場合、スキーマを神として、それに合ったバックエンドを実装するとなったならば、コードジェネレーターは必要です。むしろあったほうが良いです。スキーマが変更されたときにそれを検知し、リアルタイムで型が変更してくれるので、常に実装とスキーマがマッチすることになるからです。

ただし、サーバー側の実装でコードファーストを採用しているならば、別にコードジェネレーターは必要ありません。

もしサーバー側で NestJS Code First で実装しているのであれば、Code Generator はほとんど必要ないかなと思っています。Code First で実装している場合、実装に応じてスキーマが自動生成されるため、コードジェネレーターのメリットはクライアント側での型安全性にあると考えています。サーバー側ではその点において、それほどメリットを感じません。

要は、サーバー側でスキーマを定義し、それにコードジェネレーターを使って型を生成し、その型に合わせてバックエンドを実装していく方法は、Code First と責務が重複しているように感じます。Code First はコードを実装し、それに合わせてスキーマが生成されていくものです。そのため、コードジェネレーターとの相性は良くないかなと思っています。あるいは、必要性を感じていないとも言えます。

ただ、クライアント側ではコードジェネレーターが必要かなと思っています。その理由としては、型安全に GraphQL のクエリやミューテーションを呼び出すことができるようになるからです。

### 開発体験の違い

こちらに関しては一番最初の解決する問題の内容と重複するんですけど、まず開発スピードは上がりますよね。手動でやる場合と比べて、Code Generatorで自動で型生成してくれるのであれば、常に隙間とコードの実装は乖離しないので、ランタンエラーが起こり得ない状況を作ることができます。

ヒューマンエラーもなくすことができるので、かなり型安全かつ効率的に開発することができるようになります。

例えば、スキーマで getPot っていうクエリがあったとして、そのクエリに対して何かしらのフィールドを追加するっていう場面を想定します。手動でやってる場合は、追加したら型も手で書き換えなきゃいけないじゃないですか。それに対し、コードジェニューターを使った場合は、スキーマにフィールドを追加した段階で自動で型も変わるんですよ。

そうすると実装の方でも自動的に追加したフィールドがサジェストされるようになるし、ガードもしっかりで、フィールドを消した時も型が変わるので、その時はエラーになったりとかしますよね。なので、常にスキーマと一心同体で開発できるっていうところが最大のメリットかなと思います。

他の開発体験としては、IDE の補完で常にスキーマに合わせた型が生成されるため、IDE でサジェストされる点や、リファクタリングの安心感があると思います。スキーマを変更してもそれに追随して型も変わるため、スキーマに合ってない実装になることはまず絶対にありません。合わなかった場合はエラーとして検出されるので、その時に直せば良いです。

新人の学習コストの面でも大きいと思います。単純にスキーマと型が常に同期されているのであれば、見るべき場所は型だけで良いです。スキーマをそこまで意識する必要がなく、型だけを見れば良いので、そういったシステムの全体を把握する上で見るべき場所が減るというのは、学習コストを減らすことにもつながると思います。
